## 🎯 Core Concept

Authentication answers two questions:

- **Who is the user?** 👤
    
- **Can they access this endpoint?** 🛡️
    

In **Django REST Framework**, you can plug different authentication schemes into your API. In this course, we choose **Token Authentication** because it offers a strong balance between **simplicity** and **security**—and it’s available **out of the box**.

> [!INFO]  
> Token Auth workflow: **credentials once → token many times**  
> Instead of sending `email/password` on every request, you generate a **token** once and use it for all future authenticated calls.

---

## 🏗️ Authentication Options in DRF

### 1) 🧾 Basic Authentication

- Client sends **username/email + password** with **every request**.
    
- Often implemented via HTTP Basic headers.
    

**Why it’s not ideal:**

- Client must store credentials (high risk) 😬
    
- Credentials are repeatedly transmitted (more exposure) 🧨
    

> [!CAUTION]  
> Even with HTTPS, repeatedly sending credentials increases blast radius if client storage is compromised.

---

### 2) 🪙 Token Authentication (Chosen ✅)

- Client sends credentials **once** to get a token.
    
- Then sends **token** on each authenticated request.
    

**Why it’s good:**

- Simple to implement
    
- No extra packages needed
    
- Supported by most clients (web/mobile/desktop)
    

---

### 3) 🧩 JWT (JSON Web Tokens)

Similar concept to token auth, but commonly uses:

- **Access token** (short-lived)
    
- **Refresh token** (used to obtain new access tokens)
    

**Why people use JWT:**

- Better scalability patterns for very large systems (reduces frequent DB lookups) 🌍
    
- More complex setup (libraries + configuration)
    

> [!INFO]  
> JWT is commonly chosen when you’re operating at massive scale and want stateless verification patterns.

---

### 4) 🍪 Session Authentication

- Uses cookies + server-side session store
    
- Common for traditional websites (e.g., Django Admin)
    

**Best for:**

- Browser-based apps tightly coupled to Django templates/admin
    

---

## 🔁 Logic Flow: Token Authentication

```text
(1) Login / Token Create
Client -> POST /api/user/token/ (email + password)
       -> Server validates credentials
       -> Server creates token in DB
       -> Returns token to client

(2) Authenticated Requests
Client -> GET/PATCH /api/user/me/
       -> Adds header: Authorization: Token <token>
       -> Server checks token validity
       -> Request is authenticated
```

### Example Header ✅

```http
Authorization: Token 123abc456def...
```

---

## ✅ Pros & ❌ Cons of Token Authentication

### ✅ Pros

- 📦 **Built into DRF** (no external libraries)
    
- ⚡ **Easy to implement**
    
- 🧩 **Works with almost any client**
    
- 🔐 Avoids sending **username/password** repeatedly
    

### ❌ Cons

- 🕵️ Token must be secured on client (if stolen, attacker acts as user)
    
- 🗄️ Typically requires **DB lookup** per request to verify token
    
    - Usually fine for most apps
        
    - At huge scale, you may consider JWT
        

> [!CAUTION]  
> Token auth security is heavily influenced by **frontend storage choices**. Poor client storage = easy token theft.

---

## 🚪 Logout: Why There’s Usually No Logout API

With token auth, logout is often **client-side only**:

- ✅ Logout = **delete token locally** (local storage, cookie, keychain, etc.)
    

### Why a logout endpoint is unreliable 🤷‍♂️

Even if you create `/logout/`:

- User might uninstall the app while logged in
    
- User could lose connection / go offline
    
- Browser might clear storage/session suddenly
    

So server-side “logout events” aren’t reliable signals.

> [!INFO]  
> You _can_ create a logout endpoint (e.g., delete token from DB), but it’s optional and only worth it for specific use cases.

---

## 💡 Implementation Notes (What We’ll Do Next)

To use Token Auth in DRF you typically:

- Add an endpoint to **create tokens** (`/api/user/token/`)
    
- Protect private endpoints with:
    
    - `authentication_classes = [TokenAuthentication]`
        
    - `permission_classes = [IsAuthenticated]`
        

---

## ⚡ Pro-Tips & Gotchas

- 🔒 Always use **HTTPS** in production (tokens are secrets).
    
- 📱 Mobile apps should store tokens in secure storage (Keychain/Keystore).
    
- 🧠 If token compromise is a big concern, consider:
    
    - token rotation strategies
        
    - shorter-lived tokens (often via JWT)
        
- 🗄️ DB lookup per request is usually fine unless you’re at massive scale.
