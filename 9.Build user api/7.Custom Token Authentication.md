## 🎯 Core Concept

### ❓ Why Are We Doing This?

By default, **Django REST Framework (DRF)** provides token authentication using:

- `username`
    
- `password`
    

But in our project, we use **email as the username**.

So we need to:

1. Enable DRF's token system
    
2. Create a **custom serializer** that authenticates using `email`
    
3. Reuse DRF’s built-in token view
    
4. Override only what we need
    

> [!INFO]  
> We are leveraging DRF’s built-in logic instead of rewriting token generation from scratch. This is clean, maintainable, and production-ready.

---

## 🏗️ Logic Flow

Here’s how authentication works in this setup:

```text
POST /api/user/token/
        ↓
CreateTokenView
        ↓
AuthTokenSerializer
        ↓
authenticate()
        ↓
User Model
        ↓
Token Generated
        ↓
Response: { "token": "abc123..." }
```

### 🔄 Detailed Flow

1. Client sends `email + password`
    
2. View passes data to `AuthTokenSerializer`
    
3. `validate()` calls Django’s `authenticate()`
    
4. If valid → user attached to serializer
    
5. DRF generates token
    
6. Token returned to client

Open `settings.py` and add:

```python
INSTALLED_APPS = [
    ...
    'rest_framework.authtoken',
]
```

> [!INFO]  
> `rest_framework.authtoken` is built into DRF but must be explicitly enabled as a Django app.

## 🧠 Step 2 – Create Custom Auth Serializer

📂 `user/serializers.py`

### Required Imports

```python
from django.contrib.auth import (
    get_user_model,
    authenticate,
)
from django.utils.translation import gettext as _
from rest_framework import serializers
```

---

### 💻 AuthTokenSerializer

```python
class AuthTokenSerializer(serializers.Serializer):
    """Serializer for the user auth token."""

    email = serializers.EmailField()
    password = serializers.CharField(
        style={'input_type': 'password'},
        trim_whitespace=False
    )

    def validate(self, attrs):
        """Validate and authenticate the user."""
        email = attrs.get('email')
        password = attrs.get('password')

        user = authenticate(
            request=self.context.get('request'),
            username=email,  # Email used as username
            password=password,
        )

        if not user:
            msg = _('Unable to authenticate with provided credentials')
            raise serializers.ValidationError(
                msg,
                code='authorization'
            )

        attrs['user'] = user
        return attrs
```

---

### 🔎 Important Details

#### 🔐 `style={'input_type': 'password'}`

- Makes password hidden in DRF Browsable API
    
- Purely UI enhancement
    

#### 🚫 `trim_whitespace=False`

By default, DRF trims whitespace.

That is **dangerous for passwords** because:

```
"mypassword "  ≠  "mypassword"
```

We must preserve exact input.

> [!CAUTION]  
> Never trim passwords. Even a single space changes the hash.

---

## 🧠 What Happens Inside `validate()`?

- Extract credentials
    
- Call Django’s `authenticate()`
    
- If valid → return user
    
- If invalid → raise `ValidationError`
    
- DRF converts this to HTTP 400 automatically

## ⚙️ Step 3 – Create Token View

Instead of building everything manually, we extend DRF’s built-in view.

📂 `user/views.py`

### Imports

```python
from rest_framework.authtoken.views import ObtainAuthToken
from rest_framework.settings import api_settings
from user.serializers import AuthTokenSerializer
```

---

### 💻 CreateTokenView

```python
class CreateTokenView(ObtainAuthToken):
    """Create a new auth token for user."""

    serializer_class = AuthTokenSerializer
    renderer_classes = api_settings.DEFAULT_RENDERER_CLASSES
```

---

### 🧠 Why Override?

Default `ObtainAuthToken` expects:

```json
{
  "username": "...",
  "password": "..."
}
```

We override the serializer to accept:

```json
{
  "email": "...",
  "password": "..."
}
```

---

### 🎨 Why `renderer_classes`?

Without this line:

```python
renderer_classes = api_settings.DEFAULT_RENDERER_CLASSES
```

You may lose:

- DRF Browsable API UI
    

This restores default DRF rendering behavior.

> [!INFO]  
> This is optional but recommended for developer experience.

## ⚡ Pro-Tips & Shortcuts

### 🧩 1. Reuse Built-in DRF Views

Never rewrite token logic unless absolutely necessary.

### 🔐 2. Always Disable Whitespace Trimming for Passwords

Security + correctness issue.

### 🌍 3. Use `_()` for Translatable Error Messages

Production APIs should be i18n-ready.

### 🧪 4. Let Validation Raise Errors

Don’t manually build HTTP responses in serializers.

DRF handles it cleanly.
