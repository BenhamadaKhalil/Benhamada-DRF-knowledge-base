## 🎯 Core Concept: TDD for “Create User”

In **TDD (Test-Driven Development)**, you write the tests _first_ to describe the behavior you want:

1. ✅ Write a failing test (because feature isn’t built yet)
    
2. 🛠️ Implement the minimum code to make it pass
    
3. 🔁 Refactor safely (tests protect you)
    

So here, we’re defining what “Create User” must do **before** writing the endpoint.

---

## 🌍 Why this endpoint is “Public”

Creating an account must work **without authentication**, because a new user has **no token yet**.

That’s why these tests use a client without `.force_authenticate()`.

---

## 🧠 What the tests are checking (API contract)

These tests define the **contract** of your API:

- **Request format**: what fields the endpoint expects
    
- **Response format**: what it returns (and what it must NOT return)
    
- **Status codes**: 201 for success, 400 for invalid input
    
- **Database effect**: a user record is actually created
    
- **Security rule**: password is stored hashed, never returned

### Imports (What each one is for)

```python
from django.test import TestCase
from django.contrib.auth import get_user_model
from django.urls import reverse

from rest_framework.test import APIClient
from rest_framework import status
```

**Explanation:**

- `TestCase`: Django’s test class. It runs each test inside a **fresh test database** (isolated).
    
- `get_user_model`: returns your **current User model** (works even if you use a custom user model).
    
- `reverse`: converts a **named URL** (`'user:create'`) into a real path (`/api/user/create/`).
    
- `APIClient`: DRF’s testing client (better than Django’s default for APIs).
    
- `status`: readable HTTP status constants like `HTTP_201_CREATED`.
    

---

## 🔗 URL Constant (avoid repeating `reverse()`)

```python
CREATE_USER_URL = reverse('user:create')
```

**Why this is good:**

- You don’t hardcode `/api/user/create/`
    
- If you change your URL path later, tests still pass **as long as the name stays the same**
    
- This is best practice for long-term maintainability
    

**Why tests fail now (expected):**

- `user:create` does not exist yet → `NoReverseMatch`
    
- That’s a correct “first fail” in TDD.

## 🛠️ Helper Function: `create_user(**params)`

```python
def create_user(**params):
    """Create and return a new user."""
    return get_user_model().objects.create_user(**params)
```

### What `**params` really means

`**params` collects keyword arguments into a dict-like structure.

So this call:

```python
create_user(email='a@b.com', password='123', name='Ali')
```

becomes internally:

```python
params = {'email': 'a@b.com', 'password': '123', 'name': 'Ali'}
get_user_model().objects.create_user(**params)
```

### Why we use this helper

- Keeps tests clean (no repeated setup code)
    
- Makes it easy to create users with different payloads in future tests

## 🧪 Test Suite Class: PublicUserApiTests

```python
class PublicUserApiTests(TestCase):
    """Test the public features of the user API."""

    def setUp(self):
        self.client = APIClient()
```

**What `setUp()` does:**

- Runs **before every test method**
    
- Creates `self.client` so each test can make HTTP requests easily
    

**Why `APIClient` and not Django client?**

- DRF returns response data via `res.data`
    
- Supports auth tokens, JSON requests, DRF behaviors

## ✅ Test 1: Successful User Creation

```python
def test_create_user_success(self):
    """Test creating a user is successful."""
    payload = {
        'email': 'test@example.com',
        'password': 'testpass123',
        'name': 'Test Name',
    }

    res = self.client.post(CREATE_USER_URL, payload)

    self.assertEqual(res.status_code, status.HTTP_201_CREATED)

    user = get_user_model().objects.get(email=payload['email'])
    self.assertTrue(user.check_password(payload['password']))

    self.assertNotIn('password', res.data)
```

### Line-by-line explanation

**1) payload**

- Simulates the JSON/form data the frontend will send
    

**2) POST request**

- `self.client.post(url, payload)` sends data to your endpoint
    
- DRF test client will serialize it appropriately (often as form by default; many projects later use `format='json'`)
    

**3) status code check**

- Creating a resource should return **201 CREATED**
    
- If you returned 200, the test fails → forces correct REST design
    

**4) Fetch user from DB**

- Proves the user was actually created (not just a fake response)
    

**5) `check_password()`**

- Ensures password is **hashed**
    
- If you stored `"testpass123"` directly, `check_password()` would fail
    

**6) Password not in response**

- Even returning the password hash is a security leak
    
- This test locks the rule permanently

## ❌ Test 2: Email Already Exists

```python
def test_user_with_email_exists_error(self):
    """Test error returned if user with email exists."""
    payload = {
        'email': 'test@example.com',
        'password': 'testpass123',
        'name': 'Test Name',
    }
    create_user(**payload)

    res = self.client.post(CREATE_USER_URL, payload)

    self.assertEqual(res.status_code, status.HTTP_400_BAD_REQUEST)
```

### What this test ensures

- The API must reject duplicate emails
    
- Forces serializer validation like:
    
    - unique email constraint
        
    - or manual validation error
        

Why **400**?

- The request is invalid (violates constraints), so `400 Bad Request` is correct.

## 🔐 Test 3: Password Too Short

```python
def test_password_too_short_error(self):
    """Test an error is returned if password less than 5 chars."""
    payload = {
        'email': 'test@example.com',
        'password': 'pw',
        'name': 'Test Name',
    }

    res = self.client.post(CREATE_USER_URL, payload)

    self.assertEqual(res.status_code, status.HTTP_400_BAD_REQUEST)
    user_exists = get_user_model().objects.filter(email=payload['email']).exists()
    self.assertFalse(user_exists)
```

### Why we check both things

1. **Response is 400**
    

- Ensures the API rejects weak password input
    

2. **User is not created**
    

- Very important!  
    Sometimes developers accidentally create the user first, then validate after → database contains invalid users.
    

### Why `.exists()` is used

- It’s faster than `.get()` or `.first()`
    
- It doesn’t load full objects into memory
    
- It only checks “does at least one record exist?”

## ⚡ Pro Tips (extra clarity)

- Prefer `reverse('user:create')` to hardcoded URLs.
    
- Always test that **password is not in response**.
    
- `check_password()` is the correct way to confirm hashing.
    
- Split tests early into:
    
    - Public: register, token
        
    - Private: profile, update, /me/
