# 🧱 Step 1: Create the Serializer

📁 `user/serializers.py`

> [!CODE]

```python
"""
Serializers for the user API View.
"""

from django.contrib.auth import get_user_model
from rest_framework import serializers


class UserSerializer(serializers.ModelSerializer):
    """Serializer for the user object."""

    class Meta:
        model = get_user_model()
        fields = ['email', 'password', 'name']
        extra_kwargs = {
            'password': {
                'write_only': True,
                'min_length': 5,
            }
        }

    def create(self, validated_data):
        """Create and return a user with encrypted password."""
        return get_user_model().objects.create_user(**validated_data)
```

---

## 🧠 Why Override `create()`?

By default, `ModelSerializer` would do:

```python
User.objects.create(**validated_data)
```

⚠️ That would store the password as **plain text**.

Instead, we use:

```python
create_user()
```

Which:

- Hashes the password
    
- Applies custom manager logic
    
- Keeps authentication secure
    

> [!CAUTION]  
> Never store raw passwords. Always use `create_user()`.

---

## 🔍 Understanding `extra_kwargs`

```python
extra_kwargs = {
    'password': {
        'write_only': True,
        'min_length': 5
    }
}
```

- `write_only=True` → password is accepted but never returned
    
- `min_length=5` → triggers validation error if too short
    

If validation fails → DRF automatically returns:

```http
400 BAD REQUEST
```

# 🧱 Step 2: Create the View

📁 `user/views.py`

> [!CODE]

```python
"""
Views for the user API.
"""

from rest_framework import generics
from user.serializers import UserSerializer


class CreateUserView(generics.CreateAPIView):
    """Create a new user in the system."""
    serializer_class = UserSerializer
```

---

## 🧠 Why `CreateAPIView`?

`CreateAPIView` automatically:

- Accepts `POST`
    
- Validates serializer
    
- Calls `.create()`
    
- Returns `201 CREATED`
    
- Returns serialized data
    

Minimal code. Maximum power. 💪

# 🧱 Step 3: Add User URLs

📁 `user/urls.py`

> [!CODE]

```python
"""
URL mappings for the user API.
"""

from django.urls import path
from user import views

app_name = 'user'

urlpatterns = [
    path('create/', views.CreateUserView.as_view(), name='create'),
]
```

---

## 🧠 Why `app_name = 'user'`?

Because our test uses:

```python
reverse('user:create')
```

The `user:` namespace comes from `app_name`.

Without it → tests fail with `NoReverseMatch`.

# ⚡ Pro Tips & Gotchas

### 🔐 Always Override `create()` for User Models

Default model serializer behavior is unsafe for passwords.

---

### 🧭 Use Named URLs + reverse()

Prevents hardcoded path issues.

---

### 🧪 Validation Happens Before `create()`

If validation fails:

- `create()` is never called
    
- No DB object created
    

---

### 🏗️ Clean Layering

|Layer|Responsibility|
|---|---|
|Serializer|Validation + Transformation|
|View|HTTP handling|
|URL|Routing|
|Model Manager|Business logic (password hashing)|

This is clean DRF architecture.
