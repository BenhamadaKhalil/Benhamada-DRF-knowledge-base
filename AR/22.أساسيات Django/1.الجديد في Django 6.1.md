> **صدر في ٥ أغسطس ٢٠٢٦.** دعم أساسي حتى أبريل ٢٠٢٧، ودعم ممتدّ حتى ديسمبر ٢٠٢٧.

>
> 🇬🇧 النسخة الإنجليزية الكاملة: [[EN/22.Django Core/1.What's New in Django 6.1|What's New in Django 6.1]]

## ⚠️ اقرأ هذا أولًا — الإصدار يُقادِم أجزاءً من هذا المستودع

| الملاحظة | كانت | أصبحت |
| --- | --- | --- |
| مشكلة N+1 | `select_related` و`prefetch_related` فقط | **`fetch_mode(FETCH_PEERS)`** حلّ أصلي |
| مرجع حقول النموذج | `on_delete=CASCADE` وأخواتها | أُضيفت **`DB_CASCADE`** و`DB_SET_NULL` |
| تجزئة كلمات المرور | PBKDF2 بـ ٣٩٠٬٠٠٠ تكرار | **١٬٥٠٠٬٠٠٠** |
| Dockerfile الإنتاج | `python:3.9-alpine` | **Python 3.12–3.14 فقط** |
| إعداد قاعدة البيانات | `postgres:13-alpine` | **PostgreSQL 15+ مطلوب** |
| البريد في Celery | إعدادات `EMAIL_*` | **`MAILERS`** — القديمة مهجورة |

## ⭐ الميزة الأبرز: أوضاع الجلب

أهمّ تغيير لأي DRF API. صار لدى Django **حلٌّ مدمج لمشكلة N+1**.

```python
from django.db import models

# FETCH_ONE — الافتراضي: استعلام لكل كائن عند الوصول
for b in Book.objects.all():
    print(b.author.name)                    # N استعلامًا

# FETCH_PEERS — أول وصول يُحمّل للجميع دفعة واحدة
for b in Book.objects.fetch_mode(models.FETCH_PEERS):
    print(b.author.name)                    # استعلامان فقط

# FETCH_RAISE — ارفض التحميل الكسول واصرخ
for b in Book.objects.fetch_mode(models.FETCH_RAISE):
    print(b.author.name)                    # FieldFetchBlocked
```

**لماذا يهمّ هذا؟** `prefetch_related` يتطلّب أن **تتنبّأ** بالعلاقات التي سيلمسها المُسلسِل. أمّا `FETCH_PEERS` فيتفاعل مع ما يُلمَس فعلًا — أي أن تعديلًا في المُسلسِل لا يستطيع أن يُعيد مشكلة N+1 بصمت.

و`FETCH_RAISE` قدرة جديدة تمامًا: فعّلها في إعدادات الاختبار، فيتحوّل أي N+1 عرضي إلى **فشل صريح** بدل نقطة نهاية بطيئة.

> [!TIP] لا يُلغي `select_related`
> استعلام `JOIN` تعرف أنك تحتاجه أرخص من رحلتين إلى قاعدة البيانات. أبقِ التحميل الصريح على نقاط النهاية الساخنة، واجعل `FETCH_PEERS` شبكة أمان لما نسيته.

## 🗄️ الحذف على مستوى قاعدة البيانات

```python
from django.db.models import DB_CASCADE

author = models.ForeignKey(Author, on_delete=DB_CASCADE)
```

يُولِّد جملة `ON DELETE` حقيقية في المخطّط بدل أن يمشي Django على شجرة الكائنات في بايثون. أسرع بكثير عند الحذف الضخم.

> [!WARNING] `DB_CASCADE` لا تُطلق الإشارات
> لا `pre_delete` ولا `post_delete`. أي عمل تقوم به في إشارة حذف — تنظيف ملف مرفوع، إبطال ذاكرة مؤقّتة — يتوقّف بصمت.
>
> في هذا المشروع، صورة الوصفة تُحذَف عبر مستقبِل `post_delete`. تحويل ذلك المفتاح الأجنبي إلى `DB_CASCADE` سيترك **كل الصور يتيمة على القرص**.

## 📧 `MAILERS` تحلّ محلّ `EMAIL_*`

```python
MAILERS = {
    "default": {
        "BACKEND": "django.core.mail.backends.smtp.EmailBackend",
        "OPTIONS": {"host": "smtp.example.com", "use_tls": True},
    },
    "marketing": {
        "BACKEND": "example.third.party.EmailBackend",
        "OPTIONS": {"region": "africa-1"},
    },
}

send_mail("الموضوع", "الرسالة", "from@example.com", ["to@example.com"], using="marketing")
```

عدّة خلفيّات مُسمّاة، تختار بينها عند كل إرسال. عائلة `EMAIL_BACKEND` و`EMAIL_HOST` و`EMAIL_PORT` كلها **مهجورة** وتختفي في Django 7.0.

المشكلة التي يحلّها: الإعدادات القديمة كانت تسمح بتهيئة **واحدة** فقط، بينما كل منتج حقيقي ينتهي به الأمر إلى اثنتين — بريد المعاملات عبر مزوّد موثوق، والبريد الدعائي عبر مزوّد أرخص.

## 🔐 المصادقة

- تكرارات PBKDF2: **١٬٢٠٠٬٠٠٠ ← ١٬٥٠٠٬٠٠٠**. التجزئات القديمة تُرقّى تلقائيًا عند أول تسجيل دخول ناجح.
- إعادة تسمية `Permission.name` و`Permission.codename` مع ترحيلات.
- خاصيّة جديدة: `Permission.user_perm_str`.

---

## 💥 تغييرات كاسرة للتوافق

| التغيير | الأثر |
| --- | --- |
| `first()` و`last()` لم تعُد تُرتّب تلقائيًا بالمفتاح الأساسي | استعلام ظننته حتميًا قد لا يكون كذلك |
| أسماء SQL المستعارة صارت مُقتبَسة دائمًا | SQL الخام الذي يشير إليها قد يحتاج تعديلًا |
| `Bcc` في الترويسات صار ممنوعًا | `EmailMessage.message()` يرمي `ValueError` |
| الكوكيز الموقّعة تستخدم اشتقاق مِلح جديد | راجع التحذير أدناه |
| مفاتيح الذاكرة المؤقّتة تغيّرت للصفحات ذات ترويسات vary | أول طلب بعد النشر إخفاق مضمون |

> [!CAUTION] فخّ الكوكيز الموقّعة في الإنتاج
> النشر إلى 6.1 دون ضبط `SIGNED_COOKIE_LEGACY_SALT_FALLBACK=True` **يُخرِج كل من يحمل كوكيًا موقّعًا دفعة واحدة**. اضبطه، ثم انشر، ودع الكوكيز تتجدّد، ثم أزِله بعد أسبوع.

## 🪦 المهجورات — أصلحها الآن، تموت في 7.0

```python
# ❌ مهجور في 6.1
Entry.objects.select_related()               # بلا معاملات
Recipe.objects.values_list(flat=True)        # بلا اسم حقل صريح
transaction.savepoint()

# ✅
Entry.objects.select_related("blog", "author")
Recipe.objects.values_list("id", flat=True)
transaction.savepoint_create()
```

## 🛠️ خطة ترقية هذا المشروع

```bash
docker compose run --rm app sh -c "python -Wa manage.py test"
```

الرايةُ `-Wa` تُظهر كل `RemovedInDjango70Warning`. اعمل على القائمة حتى تصل إلى صفر قبل الترقية.

ثم بالترتيب:

1. **حدِّث الصور الأساسية** — `python:3.12-alpine` و`postgres:16-alpine`
2. **شغّل الاختبارات مع التحذيرات**، وأصلح المهجورات
3. `pip install "Django>=6.1,<6.2"`
4. `python manage.py makemigrations --check --dry-run` — إعادة تسمية `Permission` تُولّد ترحيلات
5. `python manage.py check --deploy`
6. اضبط `SIGNED_COOKIE_LEGACY_SALT_FALLBACK=True` **قبل** النشر، وأزِله بعد أسبوع
7. رحِّل `EMAIL_*` إلى `MAILERS`
8. فكّر في `FETCH_RAISE` في إعدادات الاختبار لاصطياد N+1 نهائيًا
