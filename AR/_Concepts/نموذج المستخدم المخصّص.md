# 👥 نموذج المستخدم المخصّص

> 🇬🇧 النسخة الإنجليزية: [[EN/_Concepts/Custom User Model|Custom User Model]]

---

> [!CAUTION] أنجزه في **اليوم الأول**
> تبديل نموذج المستخدم بعد وجود ترحيلات وبيانات هو أصعب إعادة هيكلة في Django على الإطلاق. لا توجد طريقة سهلة للتراجع.

---

## 🎯 لماذا أصلًا؟

`User` الافتراضي في Django يعتمد على **اسم المستخدم**. وكل تطبيق حديث تقريبًا يعتمد على **البريد الإلكتروني**. هذا هو السبب كله.

```python
# app/core/models.py
class UserManager(BaseUserManager):
    """مدير المستخدمين."""

    def create_user(self, email, password=None, **extra_fields):
        if not email:
            raise ValueError("User must have an email address.")
        user = self.model(email=self.normalize_email(email), **extra_fields)
        user.set_password(password)          # ← يُجزّئ
        user.save(using=self._db)
        return user

    def create_superuser(self, email, password):
        user = self.create_user(email, password)
        user.is_staff = True
        user.is_superuser = True
        user.save(using=self._db)
        return user


class User(AbstractBaseUser, PermissionsMixin):
    """مستخدم في النظام."""
    email = models.EmailField(max_length=255, unique=True)
    name = models.CharField(max_length=255)
    is_active = models.BooleanField(default=True)
    is_staff = models.BooleanField(default=False)

    objects = UserManager()

    USERNAME_FIELD = "email"
```

```python
# app/app/settings.py
AUTH_USER_MODEL = "core.User"
```

---

## 🧩 القطع، ولماذا كلٌّ منها موجود

| القطعة | السبب |
| --- | --- |
| `AbstractBaseUser` | يمنحك معالجة كلمة المرور و`last_login`، ولا شيء غير ذلك |
| `PermissionsMixin` | `is_superuser` والمجموعات والصلاحيات — تحتاجه لوحة الإدارة |
| `UserManager` | يستدعيه Django وأمر `createsuperuser` |
| `normalize_email` | يُصغّر حرف النطاق فلا يصير `A@Example.COM` و`a@example.com` حسابين |
| `set_password` | **يُجزّئ**. لا تُسنِد `user.password` أبدًا |
| `USERNAME_FIELD` | الحقل الذي يُصادِق Django عليه |

> [!WARNING] `authenticate()` تُسمّى معاملها `username` دائمًا
> حتى حين يكون `USERNAME_FIELD = "email"`. المعامل يرتبط بما ضبطته في `USERNAME_FIELD` أيًّا كان اسمه. ولهذا يُمرِّر `AuthTokenSerializer` القيمة هكذا:
> ```python
> authenticate(request=..., username=attrs.get("email"), password=...)
> ```

## 🔐 كلمة المرور

```python
user.set_password(raw)       # ✅ يُجزّئ
user.check_password(raw)     # ✅ يُقارن
user.password = raw          # ❌ يُخزّن نصًّا صريحًا، بصمت
```

السطر الأخير هو الخطأ، وهو **صامت تمامًا**: يبدو تسجيل الدخول ناجحًا في اختبارك اليدوي، لأن `check_password` تفشل ولم تتحقّق أنت منها.

راجع [[تجزئة كلمات المرور]].

## ⚠️ أخطاء شائعة

- **`InconsistentMigrationHistory`** ← رحّلت قبل ضبط `AUTH_USER_MODEL`. راجع [[الترحيلات]].
- **`from core.models import User`** ← استيراد دائري ويكسر التبديل. استخدم `settings.AUTH_USER_MODEL` في المفاتيح الأجنبية، و`get_user_model()` في الكود.
- **`get_user_model()` على مستوى الوحدة** ← `AppRegistryNotReady`. استدعِها **داخل** دالّة.
- **كلمة المرور تظهر في استجابة الـ API** ← ينقص `write_only` في المُسلسِل.
- **الاختبارات بطيئة جدًا** ← التجزئة مُكلفة عن قصد. استخدم مُجزِّئًا سريعًا في إعدادات **الاختبار فقط**.
