# 🔒 المعاملات — Transactions

> نصف كتابة أسوأ من لا كتابة. المعاملة هي كيف تجعل «كلّها أو لا شيء» حقيقة.
>
> 🇬🇧 النسخة الإنجليزية: [[EN/19.Production DRF/8.Transactions|Transactions]]

---

## 🎯 المشكلة

نقطة إنشاء الوصفة تكتب في **ثلاثة** جداول:

```python
def create(self, validated_data):
    tags = validated_data.pop("tags", [])
    ingredients = validated_data.pop("ingredients", [])
    recipe = Recipe.objects.create(**validated_data)      # ① core_recipe
    self._get_or_create_tags(tags, recipe)                # ② core_tag + جدول الوصل
    self._get_or_create_ingredients(ingredients, recipe)  # ③ core_ingredient
    return recipe
```

إن رمى ③ استثناءً — بيانات خاطئة، أو خرق قيد، أو انقطاع قاعدة البيانات — فإن ① و② **مُثبَّتان بالفعل**. صار لديك وصفة بوسوم وبلا مكوّنات، وتلقّى العميل `500` يُخبره أن العملية فشلت.

## 🛠️ ثلاث طرق للتطبيق

### ١. مدير السياق — الأدقّ

```python
from django.db import transaction


def create(self, validated_data):
    tags = validated_data.pop("tags", [])
    ingredients = validated_data.pop("ingredients", [])

    with transaction.atomic():
        recipe = Recipe.objects.create(**validated_data)
        self._get_or_create_tags(tags, recipe)
        self._get_or_create_ingredients(ingredients, recipe)

    return recipe
```

يُغلّف ما يحتاج التغليف بالضبط. **فضّله.**

### ٢. المُزيِّن

```python
@transaction.atomic
def perform_create(self, serializer):
    serializer.save(user=self.request.user)
```

### ٣. `ATOMIC_REQUESTS` — كل طلب في معاملة

```python
DATABASES = {"default": {..., "ATOMIC_REQUESTS": True}}
```

آمن افتراضيًا، لكنه يُبقي اتصال قاعدة البيانات مفتوحًا طوال **كامل** الطلب — بما في ذلك أي استدعاء HTTP خارجي بطيء داخل عرضك. تحت الحِمل يستنزف ذلك مجمّع الاتصالات.

## ⚠️ الأفخاخ الأربعة

### ١. التقاط استثناء **داخل** `atomic()` يكسرها

```python
# ❌ TransactionManagementError عند الاستعلام التالي
with transaction.atomic():
    try:
        Recipe.objects.create(**data)
    except IntegrityError:
        pass
    Tag.objects.create(...)     # 💥 "An error occurred in the current transaction"

# ✅ استخدم نقطة حفظ متداخلة
with transaction.atomic():
    try:
        with transaction.atomic():
            Recipe.objects.create(**data)
    except IntegrityError:
        pass
    Tag.objects.create(...)     # يعمل
```

بمجرّد وقوع خطأ في قاعدة البيانات تُصبح المعاملة **مسمومة**. يرفض Django أي استعلام لاحق حتى تتراجع إلى نقطة حفظ — وكتلة `atomic()` الداخلية **هي** تلك النقطة.

> [!INFO] Django 6.1 غيّر اسم الدالّة منخفضة المستوى
> `transaction.savepoint()` مهجورة؛ استخدم **`savepoint_create()`**. نادرًا ما تحتاجها مباشرةً — الكتلة المتداخلة هي الأسلوب المُعتاد.

### ٢. الآثار الجانبية تنطلق قبل التثبيت

```python
# ❌ البريد يُرسَل، ثم تتراجع المعاملة
with transaction.atomic():
    recipe = Recipe.objects.create(**data)
    send_notification_email(recipe)      # 💥 لا يمكن التراجع عنه
    risky_operation()                    # يرمي استثناءً

# ✅ أجّله حتى يقع التثبيت فعلًا
with transaction.atomic():
    recipe = Recipe.objects.create(**data)
    transaction.on_commit(lambda: send_notification_email(recipe))
    risky_operation()
```

`on_commit` هو المكان الصحيح **لكل ما لا تستطيع قاعدة البيانات التراجع عنه**: البريد، الـ webhooks، إبطال الذاكرة المؤقّتة، الإشعارات، وخصوصًا [[9.المهامّ الخلفية مع Celery|مهامّ Celery]].

> [!CAUTION] سباق Celery الكلاسيكي
> ```python
> with transaction.atomic():
>     recipe = Recipe.objects.create(**data)
>     process_recipe.delay(recipe.id)     # ❌ العامل قد يبدأ قبل التثبيت
> ```
> يلتقط العامل المهمّة، ويبحث عن `recipe.id`، فيحصل على `DoesNotExist` — لأن الصفّ لم يُثبَّت بعد. متقطّع، لا يتكرّر محلّيًا، ومستمرّ في الإنتاج. دائمًا:
> ```python
> transaction.on_commit(lambda: process_recipe.delay(recipe.id))
> ```

### ٣. طلبان متزامنان يدهسان بعضهما

```python
# ❌ تحديث ضائع
recipe = Recipe.objects.get(id=1)
recipe.views_count += 1        # قرأ ١٠
recipe.save()                  # كتب ١١ — وكذلك فعل الطلب الآخر

# ✅ دع قاعدة البيانات تُجري الحساب
from django.db.models import F
Recipe.objects.filter(id=1).update(views_count=F("views_count") + 1)

# ✅ أو اقفل الصفّ
with transaction.atomic():
    recipe = Recipe.objects.select_for_update().get(id=1)
    recipe.views_count += 1
    recipe.save()
```

`F()` هو `UPDATE … SET x = x + 1` ذرّي بلا قفل. و`select_for_update()` يُمسك قفلًا على الصفّ حتى نهاية المعاملة — صحيح حين يجب أن تقرأ ثم تُقرّر ثم تكتب.

### ٤. الاختبارات تُخفي أخطاء المعاملات

`TestCase` يُغلّف كل اختبار في معاملة ويتراجع عنها. أي أن استدعاءات `on_commit` **لا تعمل إطلاقًا** في `TestCase` عادي:

```python
def test_notification_sent_on_commit(self):
    with self.captureOnCommitCallbacks(execute=True) as callbacks:
        self.client.post(RECIPES_URL, payload, format="json")

    self.assertEqual(len(callbacks), 1)
```

بدون `captureOnCommitCallbacks(execute=True)` ستكتب كودًا في `on_commit` **لا تُشغّله مجموعة اختباراتك ولو مرة واحدة**.

## 🎯 متى تحتاج معاملة؟

| الحالة | مطلوبة؟ |
| --- | --- |
| `Model.objects.create()` واحد | ❌ ذرّي أصلًا |
| كتابة متداخلة عبر جدولين أو أكثر | ✅ **دائمًا** |
| اقرأ ← قرّر ← اكتب | ✅ مع `select_for_update` |
| زيادة عدّاد | ✅ أو استخدم `F()` |
| مال، مخزون، حجوزات | ✅ غير قابل للتفاوض |
| نقطة نهاية للقراءة فقط | ❌ |
| عرض يستدعي API خارجيًا | ⚠️ أبقِ الاستدعاء **خارج** الكتلة |
