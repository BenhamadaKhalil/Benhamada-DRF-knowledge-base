# 🐳 أوامر Docker و Compose

> النمط الذي يحكم كل شيء في هذا المشروع:
> `docker compose run --rm app sh -c "<أمر Django>"`
>
> 🇬🇧 النسخة الإنجليزية: [[EN/20.Reference/6.Docker and Compose Commands|Docker and Compose Commands]]

---

## 🔑 تشريح الأمر

| الجزء | لماذا |
| --- | --- |
| `docker compose` | صيغة الإصدار الثاني (بمسافة). `docker-compose` هو الملف التنفيذي القديم |
| `run` | يُشغّل حاوية **لمرة واحدة** لهذا الأمر |
| `--rm` | يحذف الحاوية بعدها — بدونها تتراكم إلى الأبد |
| `app` | اسم الخدمة في `docker-compose.yml` |
| `sh -c "…"` | يُشغّل النصّ كاملًا كأمر واحد، فيعمل `&&` |

```bash
docker compose run --rm app sh -c "python manage.py test && flake8"
```

بدون `sh -c` يكون `python` وحده هو الأمر، ويُمرَّر `&& flake8` إلى Django كمعاملات.

## ▶️ الاستخدام اليومي

```bash
docker compose up
```

```bash
docker compose up -d
```

```bash
docker compose down
```

```bash
docker compose logs -f app
```

```bash
docker compose ps
```

| الأمر | يفعل |
| --- | --- |
| `up` | يبني إن لزم، ويُنشئ ويُشغّل ويعرض السجلّات |
| `up --build` | يُجبر إعادة البناء أولًا |
| `down` | يُوقف ويحذف الحاويات والشبكة |
| `down -v` | **يحذف الأحجام المُسمّاة أيضًا — أي قاعدة بياناتك** |
| `exec app sh` | صدفة داخل حاوية **قيد التشغيل** |
| `run --rm app sh` | صدفة في حاوية **جديدة مؤقّتة** |

> [!CAUTION] `down -v` يحذف بياناتك
> الراية `-v` تحذف الأحجام المُسمّاة، ومنها `dev-db-data` — قاعدة بياناتك المحلّية كاملة. هي الأمر الصحيح حين **تريد** بداية نظيفة (مثل إصلاح `InconsistentMigrationHistory`)، وكارثة في غير ذلك.

## 🏗️ البناء

```bash
docker compose build
```

```bash
docker compose build --no-cache
```

```bash
docker compose -f docker-compose-deploy.yml build app
```

> [!TIP] لماذا يهمّ ترتيب الأسطر في الـ Dockerfile؟
> `COPY requirements.txt` ← `RUN pip install` ← `COPY ./app` يعني أن تعديل الكود يُعيد استخدام طبقة الاعتماديات المُخزَّنة. لو نسخت التطبيق أولًا، لأعاد كل تعديل تثبيت كل الحزم.

## 🚀 نشر الإنتاج

```bash
docker compose -f docker-compose-deploy.yml up -d --build
```

```bash
docker compose -f docker-compose-deploy.yml logs -f
```

```bash
docker compose -f docker-compose-deploy.yml config
```

`config` يطبع الملف بعد استبدال كل المتغيّرات — **أسرع طريقة لمعرفة لماذا `${VAR}` فارغ**.

## 🗄️ الوصول إلى قاعدة البيانات

```bash
docker compose exec db psql -U devuser -d devdb
```

```bash
docker compose exec db pg_dump -U devuser devdb > backup.sql
```

| أمر `psql` | يعرض |
| --- | --- |
| `\dt` | الجداول |
| `\d core_recipe` | أعمدة جدول وفهارسه |
| `\l` | قواعد البيانات |
| `\q` | خروج |

## 🧹 التنظيف

```bash
docker system df
```

```bash
docker image prune -a
```

> [!CAUTION] اقرأ الرايات قبل `prune`
> `docker system prune -a --volumes` يحذف **كل** صورة وحاوية وشبكة **وحجم** غير مستخدم على الجهاز — بما في ذلك قواعد بيانات مشاريع أخرى. `-a` وحدها هي المطلوب عادةً.

## 🔍 التصحيح

| العَرَض | أول أمر |
| --- | --- |
| الحاوية تخرج فورًا | `docker compose logs app` |
| «connection refused» لقاعدة البيانات | `docker compose ps` — هل `db` يعمل؟ |
| متغيّر بيئة يبدو فارغًا | `docker compose config` |
| ملفات ثابتة 404 | `exec app sh -c "ls /vol/web/static"` |
| تعديلات الكود لا تظهر | تحقّق من ربط الحجم في `docker-compose.yml` |
| القرص ممتلئ | `docker system df` |

## 📄 ملف compose مشروحًا

```yaml
services:
  app:
    build:
      context: .
      args:
        - DEV=true            # ← يقابل ARG في الـ Dockerfile
    ports:
      - "8000:8000"           # المضيف:الحاوية
    volumes:
      - ./app:/app            # إعادة تحميل حيّة — للتطوير فقط
    command: >
      sh -c "python manage.py wait_for_db &&
             python manage.py migrate &&
             python manage.py runserver 0.0.0.0:8000"
    environment:
      - DB_HOST=db            # اسم **الخدمة** يُحَلّ عبر DNS الداخلي
    depends_on:
      - db                    # ترتيب البدء فقط — لا الجاهزية

  db:
    image: postgres:16-alpine   # Django 6.1 يتطلّب PostgreSQL 15+
    volumes:
      - dev-db-data:/var/lib/postgresql/data

volumes:
  dev-db-data:
```

نقطتان تستحقّان الترسيخ:

- **`0.0.0.0:8000` لا `127.0.0.1:8000`.** الربط بـ localhost داخل حاوية يعني أن الحاوية وحدها تصل إليه، ويصبح ربط المنفذ بلا فائدة.
- **`depends_on` ترتيب بدء لا جاهزية.** بدء حاوية `db` لا يعني أن Postgres يقبل الاتصالات. هذه الفجوة بالضبط هي سبب وجود `wait_for_db`.
