# Django – Run `wait_for_db` + `migrate` Automatically (Docker Compose + CI)

## 📌 Lesson Goal
Make the project start reliably by ensuring we always:

1) wait for the database  
2) apply migrations  
3) start the server  

And also do the same in CI (GitHub Actions) so tests don’t fail due to DB not being ready.

---

# 🐳 Part 1 – Update `docker-compose.yml` Command

We modify the **app service command** so it runs multiple management commands in order.

### ✅ New startup sequence
- `python manage.py wait_for_db`
- `python manage.py migrate`
- `python manage.py runserver 0.0.0.0:8000`

Example (conceptually):

```yaml
command: >
  sh -c "python manage.py wait_for_db &&
         python manage.py migrate &&
         python manage.py runserver 0.0.0.0:8000"
```

### Why `&&`?
`&&` means:
- run the next command only if the previous one succeeded

So:
- server won’t start unless DB is ready
- migrations won’t run unless DB is ready
- server won’t start unless migrations succeeded

✅ This makes startup reliable.

---

# ✅ Test the Setup Locally

Stop and restart:

```bash
docker-compose down
docker-compose up
```

Expected output:
- `Waiting for database...`
- `Database available!`
- migration logs
- server starts normally

Then you can open the browser and confirm the app runs.

---

# 🤖 Part 2 – Update CI/CD (GitHub Actions Checks)

Problem:
- tests depend on DB being available
- CI can start app/tests before DB is ready → flaky failures

Solution:
Add `wait_for_db` before running tests.

### Example idea:
Inside the GitHub Actions step that runs tests:

```bash
python manage.py wait_for_db &&
python manage.py test
```

✅ Ensures DB is ready before the test suite executes.

# 🔥 Key Takeaways
- `depends_on` only ensures the DB container starts, not that Postgres is ready
- `wait_for_db` solves DB readiness timing issues
- `migrate` should run after DB is available
- Best practice startup flow:
  `wait_for_db → migrate → runserver`
- CI should run `wait_for_db` before tests to avoid random failures
