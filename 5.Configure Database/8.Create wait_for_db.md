# Django – Create `wait_for_db` Management Command (TDD Setup)

## 📌 Lesson Goal
Add a **custom Django management command** called `wait_for_db`, and write unit tests first (Test Driven Development) before implementing the logic.

This command will later solve the Docker Compose DB race condition by:
- repeatedly checking DB readiness
- waiting between retries
- continuing only when DB is available

---

# 🧱 Step 1 – Create Command Folder Structure

Inside the `core` app, create this structure:

```
core/
└── management/
    ├── __init__.py
    └── commands/
        ├── __init__.py
        └── wait_for_db.py
```

✅ Django automatically detects management commands when they follow this structure.  
Then you can run it with:

```bash
python manage.py wait_for_db
```

# 🧪 Step 3 – Create Unit Tests First (TDD)

Create test file:

```
core/tests/test_commands.py
```

Add imports:

```python
"""Test custom Django management commands."""

from unittest.mock import patch

from psycopg2 import OperationalError as Psycopg2Error
from django.core.management import call_command
from django.db.utils import OperationalError
from django.test import SimpleTestCase
```

### Why `SimpleTestCase`?
We are testing behavior where the database may NOT be available.
`SimpleTestCase` avoids DB setup/migrations and keeps tests fast.

---

# ✅ Test Case 1 – DB Ready Immediately

If the DB is ready, the command should:
- call `check()`
- succeed immediately
- not loop / not delay

Mock Django’s `Command.check()` method:

```python
@patch('core.management.commands.wait_for_db.Command.check')
def test_wait_for_db_ready(self, patched_check):
    """Test waiting for database if database ready."""
    patched_check.return_value = True

    call_command('wait_for_db')

    patched_check.assert_called_once_with(databases=['default'])
```

### What this test guarantees
- The command exists and can be called
- It calls Django’s built-in `check()` to verify DB connectivity

Result at this stage:
✅ Test runs but fails (because command isn’t implemented yet)  
Expected failure: `check called 0 times`

---

# ⏳ Test Case 2 – DB Not Ready (Retry + Delay)

We simulate DB startup phases by raising errors first, then succeeding.

Two types of errors:
- `Psycopg2Error` (database server not ready / connection refused)
- `django.db.utils.OperationalError` (DB up but not fully usable yet)

Mock sequence:

- 2 × `Psycopg2Error`
- 3 × `OperationalError`
- then `True`

Also mock `time.sleep()` so tests don’t actually pause.

```python
@patch('time.sleep')
@patch('core.management.commands.wait_for_db.Command.check')
def test_wait_for_db_delay(self, patched_check, patched_sleep):
    """Test waiting for database when getting OperationalError."""
    patched_check.side_effect = (
        [Psycopg2Error] * 2 +
        [OperationalError] * 3 +
        [True]
    )

    call_command('wait_for_db')

    self.assertEqual(patched_check.call_count, 6)
    patched_check.assert_called_with(databases=['default'])
```

### Why mock `sleep`?
We want retry behavior without slowing tests down.

# 🔥 Key Takeaways

- Django finds custom commands using `management/commands/`
- `BaseCommand` + `handle()` is the entry point
- `call_command()` is used to test commands
- `patch()` lets us simulate DB behavior
- Use `SimpleTestCase` when no DB is needed
- TDD workflow: **write test → fail → implement → pass**
