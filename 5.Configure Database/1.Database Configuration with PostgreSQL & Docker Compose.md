# Django – Database Configuration with PostgreSQL & Docker Compose

## 📌 Section Goal

Configure a PostgreSQL database for a Django Recipe Project using Docker Compose.

This setup will:
- Use PostgreSQL as the database
- Use Docker Compose to manage services
- Enable persistent data storage
- Use environment variables for configuration

---

# 🐘 Why PostgreSQL?

## What is PostgreSQL?

PostgreSQL (Postgres) is:
- Open-source
- Free for personal & commercial use
- Production-ready
- Officially supported by Django

Django includes built-in support for PostgreSQL in its official documentation.

📎 This makes it one of the safest and most recommended choices for Django projects.

---

# 🐳 Why Use Docker Compose?

Instead of installing PostgreSQL directly on our machine, we use Docker Compose.

## Benefits:

### 1️⃣ Reproducibility
Database configuration lives inside the project source code.
- Other developers can run the project easily
- Moving between machines is simple
- Deployment environment matches development

### 2️⃣ Persistent Volumes
Data remains saved even if containers stop/start.

Without volumes:
- Database resets every time container stops

With volumes:
- Data stays until manually deleted

Very important during development.

### 3️⃣ Automatic Networking
Docker Compose automatically:
- Creates a network between services
- Handles internal communication
- Avoids manual port configuration headaches

### 4️⃣ Environment Variables
Docker Compose allows:
- Database credentials
- Host configuration
- Settings injection

All without hardcoding values in your code.

# 🏗️ Architecture Overview

We will have **two services**:

## 1️⃣ Database Service (db)
- Runs PostgreSQL
- Stores data

## 2️⃣ App Service (app)
- Runs Django
- Connects to database
- Reads and writes data

---

# 🔗 How Services Communicate

Docker Compose automatically creates a network.

Inside the Django app configuration:

- The hostname of the database = service name
- If service is named `db`, then Django connects to host `db`

Example conceptually:

```python
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'HOST': 'db',
    }
}
````

You use the service name as the hostname.

---

# ⏳ `depends_on` in Docker Compose

We use:

```yaml
depends_on:
  - db
```

This ensures:

- Database container starts before app container
    

⚠ Important:

Starting ≠ Ready.

Even if the container starts,  
the database inside may not be ready yet.

This causes a **race condition**.

The course will later cover how to properly wait for database readiness.

# 💾 Persistent Data with Volumes

## Problem

Containers are temporary.  
If deleted → data is lost.

## Solution: Named Volumes

We define a volume in Docker Compose:

```yaml
volumes:
  postgres_data:
```

Then map it inside the db service:

```yaml
services:
  db:
    volumes:
      - postgres_data:/var/lib/postgresql/data
```

## What Happens Here?

- `/var/lib/postgresql/data` is the location where Postgres stores its data
    
- This path comes from official PostgreSQL Docker documentation
    
- Docker maps it to a named volume on your machine
    

Now:

- Restart container → data stays
    
- Stop container → data stays
    
- Delete volume → data gone
    

You control when data is cleared.

---

# 🧠 Key Concepts to Remember

- PostgreSQL is production-grade and officially supported by Django.
    
- Docker Compose allows multi-service architecture.
    
- Services communicate using service names as hostnames.
    
- `depends_on` controls startup order, NOT readiness.
    
- Named volumes allow persistent database storage.
    
- Environment variables prevent hardcoding credentials.
