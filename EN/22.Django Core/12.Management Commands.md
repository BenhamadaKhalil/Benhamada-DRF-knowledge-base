## 🎯 Anatomy

A command is a `Command` class in a very specific place:

```text
app/core/
├── management/
│   ├── __init__.py          ← required
│   └── commands/
│       ├── __init__.py      ← required
│       └── wait_for_db.py   ← filename IS the command name
```

> [!WARNING] Both `__init__.py` files are required
> Miss either and `manage.py` reports `Unknown command` with no hint as to why. This is the single most common failure, and it's silent.

```python
# app/core/management/commands/wait_for_db.py
import time

from psycopg2 import OperationalError as Psycopg2OpError
from django.db.utils import OperationalError
from django.core.management.base import BaseCommand


class Command(BaseCommand):
    """Django command to wait for the database to be available."""

    help = "Block until the database accepts connections."

    def handle(self, *args, **options):
        self.stdout.write("Waiting for database...")
        db_up = False

        while db_up is False:
            try:
                self.check(databases=["default"])
                db_up = True
            except (Psycopg2OpError, OperationalError):
                self.stdout.write("Database unavailable, waiting 1 second...")
                time.sleep(1)

        self.stdout.write(self.style.SUCCESS("Database available!"))
```

```bash
docker compose run --rm app sh -c "python manage.py wait_for_db"
```

**Why this exists:** `depends_on` in Compose waits for the *container* to start, not for Postgres to accept connections. That gap is a real race, and it's the same problem in Kubernetes (readiness probes) and on any orchestrated platform. See [[6.Fixing Database Race Condition]].

## 🎨 Output styling

```python
self.stdout.write("plain")
self.stdout.write(self.style.SUCCESS("green"))
self.stdout.write(self.style.WARNING("yellow"))
self.stdout.write(self.style.ERROR("red"))
self.stderr.write(self.style.ERROR("to stderr"))
```

Use `self.stdout.write`, not `print()` — it respects `--no-color`, is redirectable, and can be captured in tests.

## 🎛️ Arguments

```python
class Command(BaseCommand):
    help = "Delete recipes older than N days."

    def add_arguments(self, parser):
        parser.add_argument("days", type=int, help="Age threshold in days")
        parser.add_argument("--dry-run", action="store_true", help="Report only")
        parser.add_argument("--user", type=str, help="Limit to one user's recipes")

    def handle(self, *args, **options):
        cutoff = timezone.now() - timedelta(days=options["days"])
        qs = Recipe.objects.filter(created_at__lt=cutoff)

        if options["user"]:
            qs = qs.filter(user__email=options["user"])

        count = qs.count()

        if options["dry_run"]:
            self.stdout.write(self.style.WARNING(f"Would delete {count} recipes."))
            return

        qs.delete()
        self.stdout.write(self.style.SUCCESS(f"Deleted {count} recipes."))
```

```bash
docker compose run --rm app sh -c "python manage.py prune_recipes 30 --dry-run"
```

It's plain `argparse`. **Always give a destructive command a `--dry-run`** — you will run it against production eventually.

## 🧪 Testing a command

```python
from unittest.mock import patch

from django.core.management import call_command
from django.db.utils import OperationalError
from django.test import SimpleTestCase


@patch("core.management.commands.wait_for_db.Command.check")
class CommandTests(SimpleTestCase):

    def test_wait_for_db_ready(self, patched_check):
        """Test waiting for database when database is ready."""
        patched_check.return_value = True

        call_command("wait_for_db")

        patched_check.assert_called_once_with(databases=["default"])

    @patch("time.sleep")
    def test_wait_for_db_delay(self, patched_sleep, patched_check):
        """Test waiting for database when getting OperationalError."""
        patched_check.side_effect = [Psycopg2Error] * 2 + [OperationalError] * 3 + [True]

        call_command("wait_for_db")

        self.assertEqual(patched_check.call_count, 6)
```

Three things worth noticing:

- **`SimpleTestCase`** — no database needed, so the test is fast and honest about its dependencies
- **`@patch("time.sleep")`** — otherwise the test genuinely sleeps 5 seconds
- **Decorator order is inside-out** — the closest decorator is the first argument after `self`

Capture output with `call_command("cmd", stdout=StringIO())`.

## 📅 Commands + cron

The lightest possible scheduled job, before you reach for [[9.Background Jobs with Celery|Celery Beat]]:

```bash
0 3 * * * cd ~/recipe-api && docker compose -f docker-compose-deploy.yml run --rm app sh -c "python manage.py prune_recipes 90"
```

> [!TIP] When cron beats Celery
> If the work is *purely periodic* — a nightly cleanup, a weekly digest — a management command on cron needs no broker, no worker container, and no result backend. Celery earns its complexity when you need retries, chaining, and event-driven (not just time-driven) work.

## 🧰 Built-in commands worth knowing

| Command | Does |
| --- | --- |
| `check --deploy` | audits security settings |
| `diffsettings` | shows only what differs from Django's defaults |
| `showmigrations` | which migrations are applied |
| `sqlmigrate app 0002` | the SQL a migration will run |
| `dbshell` | psql, with your settings' credentials |
| `shell -c "..."` | run a one-liner with models loaded |
| `dumpdata` / `loaddata` | fixtures |
| `createsuperuser --noinput` | scriptable, with env vars |
| `collectstatic --noinput` | gather static files |
| `flush` | empty the database, keep the schema |

## ⚠️ Gotchas

- **`Unknown command`** → a missing `__init__.py`, or the app isn't in `INSTALLED_APPS`.
- **Command not found in Docker** → you rebuilt the image but the file is only in the host volume, or vice versa.
- **`print()` output missing in Docker** → `PYTHONUNBUFFERED=1`.
- **A long-running command holds a DB connection open** → call `connection.close()` between chunks in batch jobs.
- **No `--dry-run` on a destructive command** → you'll regret it exactly once.
