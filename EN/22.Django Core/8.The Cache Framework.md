# 🗄️ The Cache Framework

> 📖 [topics/cache](https://docs.djangoproject.com/en/6.1/topics/cache/)
>
> The *strategy* — what's worth caching, and invalidation — is [[3.Caching]]. This note is Django's machinery.

## 🔌 Backends

```python
CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.redis.RedisCache",
        "LOCATION": os.environ.get("REDIS_URL", "redis://redis:6379/1"),
        "TIMEOUT": 300,
        "KEY_PREFIX": "recipeapi",
    }
}
```

| Backend | Shared across processes? | Use for |
| --- | --- | --- |
| `redis.RedisCache` | ✅ | **production** — built in since Django 4.0, no third-party package |
| `memcached.PyMemcacheCache` | ✅ | production, if you already run memcached |
| `db.DatabaseCache` | ✅ | no Redis available; needs `createcachetable` |
| `filebased.FileBasedCache` | ✅ (same host) | single-server, low volume |
| `locmem.LocMemCache` | ❌ **per process** | the default — dev only |
| `dummy.DummyCache` | — | tests; caching code runs but never hits |

> [!CAUTION] `LocMemCache` is the default, and it is per-process
> With four uWSGI workers you have four independent caches. Hit rate collapses, and anything that *depends* on the cache for correctness silently breaks — most importantly [[2.Throttling and Rate Limiting|throttling]], where a 5/minute limit becomes 20/minute.

## 🧰 The low-level API

```python
from django.core.cache import cache

cache.set("key", value, timeout=300)      # timeout=None = forever, 0 = don't cache
cache.get("key")                          # None if missing
cache.get("key", "default")
cache.get_or_set("key", expensive_fn, 300)
cache.add("key", value)                   # only if absent — returns False if present
cache.touch("key", 600)                   # extend the TTL without re-fetching
cache.delete("key")
cache.delete_many(["a", "b"])
cache.clear()                             # ⚠️ the WHOLE cache

cache.incr("counter")                     # atomic
cache.decr("counter")

cache.set_many({"a": 1, "b": 2}, 300)     # one round trip
cache.get_many(["a", "b"])                # {"a": 1, "b": 2}
```

The pattern is always **key → get → miss → compute → set → return**:

```python
def get_user_recipe_stats(user):
    key = f"recipe_stats:{user.id}"
    stats = cache.get(key)

    if stats is None:
        stats = {"total": Recipe.objects.filter(user=user).count()}
        cache.set(key, stats, timeout=600)

    return stats
```

> [!TIP] `cache.add()` is a poor man's lock
> ```python
> if cache.add("job:nightly:lock", "1", timeout=3600):
>     run_the_job()
> ```
> `add` is atomic and returns `False` if the key exists — so only one worker proceeds. Useful for making a [[9.Background Jobs with Celery|Celery task]] idempotent. Not a substitute for a real distributed lock when correctness depends on it.

## 🔑 Key discipline

Django transforms your key before storing it:

```text
KEY_PREFIX : VERSION : your_key
recipeapi  :    1    : recipe_stats:42
```

`KEY_PREFIX` lets several apps share one Redis instance. `VERSION` gives you a global invalidation lever:

```python
cache.set("k", v, version=2)
cache.incr_version("k")
```

Keys are limited to 250 characters and must not contain spaces or control characters — memcached's constraints, which Django enforces everywhere for portability. Hash long keys yourself.

## 🌐 The per-view and per-site caches

```python
from django.views.decorators.cache import cache_page
from django.views.decorators.vary import vary_on_headers


@cache_page(60 * 5)
@vary_on_headers("Authorization")
def my_view(request):
    ...
```

In a ViewSet:

```python
from django.utils.decorators import method_decorator


class RecipeViewSet(viewsets.ModelViewSet):
    @method_decorator(cache_page(60 * 5))
    @method_decorator(vary_on_headers("Authorization"))
    def list(self, request, *args, **kwargs):
        return super().list(request, *args, **kwargs)
```

> [!CAUTION] `vary_on_headers("Authorization")` is load-bearing
> The default cache key is built from the **URL only**. Without varying on the auth header, the first user's recipe list is served to every user. Treat a missing `Vary` on an authenticated cached response as a security bug, not a performance one.

Per-view caching is a poor fit for a per-user API in general — it shines on genuinely public, identical-for-everyone endpoints. Reach for the low-level API instead.

> [!INFO] Django 6.1 changed cache keys for varied responses
> Pages and fragments with vary headers use a new key derivation, so the **first request after upgrading is a guaranteed miss**. Harmless, but expect a brief load spike.

## 🧪 Caching in tests

```python
@override_settings(CACHES={"default": {"BACKEND": "django.core.cache.backends.dummy.DummyCache"}})
class MyTests(TestCase):
    ...
```

or, when you're testing cache behaviour itself:

```python
def setUp(self):
    cache.clear()

def tearDown(self):
    cache.clear()
```

Throttle tests **require** this — counters leak between tests and you get failures that depend on ordering. See [[5.Testing Patterns]].

## ⚠️ Gotchas

- **Cache never hits** → per-process `LocMemCache`, or a key that varies each call (a timestamp in the key).
- **`cache.incr` raises `ValueError`** → the key doesn't exist. `incr` never creates; `cache.set(key, 0)` first.
- **Redis memory grows without bound** → no eviction policy. Set `maxmemory-policy allkeys-lru` so Redis evicts instead of OOMing.
- **Pickled model instances go stale** → cache IDs and primitives, not model objects.
- **`cache.clear()` in production** → clears everything, including other apps sharing the Redis database. Use a `KEY_PREFIX` and delete by pattern instead.
- **`TIMEOUT: None` means forever**, but `timeout=0` means *don't cache at all*. Easy to swap by accident.
