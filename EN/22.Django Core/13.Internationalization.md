## ⚙️ Settings

```python
# app/app/settings.py
USE_I18N = True          # translation machinery on
USE_L10N = True          # locale-aware number and date formatting
USE_TZ = True            # store datetimes in UTC  ← always
LANGUAGE_CODE = "en-us"
TIME_ZONE = "UTC"

LANGUAGES = [
    ("en", "English"),
    ("ar", "العربية"),
    ("fr", "Français"),
]

LOCALE_PATHS = [BASE_DIR / "locale"]
```

```python
MIDDLEWARE = [
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.locale.LocaleMiddleware",     # ← after session, before common
    "django.middleware.common.CommonMiddleware",
    ...
]
```

`LocaleMiddleware` picks the active language per request, in this order: URL prefix → session → cookie → `Accept-Language` header → `LANGUAGE_CODE`.

## 🔤 Marking strings

```python
from django.utils.translation import gettext_lazy as _


class Recipe(models.Model):
    title = models.CharField(_("title"), max_length=255)
    time_minutes = models.IntegerField(_("time in minutes"))

    class Meta:
        verbose_name = _("recipe")
        verbose_name_plural = _("recipes")
```

```python
from django.utils.translation import gettext as _

def my_view(request):
    message = _("Recipe saved successfully.")
```

> [!WARNING] `gettext` vs `gettext_lazy` — this one matters
> **`gettext_lazy`** at module level: models, forms, serializers, settings. It defers translation until the string is rendered, so it picks up the *request's* language.
> **`gettext`** inside functions that run per-request.
>
> Using plain `gettext` at module level freezes the translation to whatever language was active at **import time** — meaning every user sees the server's startup language. It works in dev (one language) and fails in production, silently.

Plurals:

```python
from django.utils.translation import ngettext

msg = ngettext(
    "%(count)d recipe found.",
    "%(count)d recipes found.",
    count,
) % {"count": count}
```

Arabic has **six** plural forms. `ngettext` handles that from the locale's plural rule; string concatenation cannot.

## 🔧 The workflow

```bash
docker compose run --rm app sh -c "python manage.py makemessages -l ar"
```

```bash
docker compose run --rm app sh -c "python manage.py compilemessages"
```

```text
locale/
└── ar/
    └── LC_MESSAGES/
        ├── django.po     ← you edit this
        └── django.mo     ← compiled; Django reads this
```

```po
#: core/models.py:24
msgid "title"
msgstr "العنوان"

#: recipe/views.py:88
msgid "Recipe saved successfully."
msgstr "تم حفظ الوصفة بنجاح."
```

`.po` is committed; `.mo` is generated. Re-run `compilemessages` on every deploy — an un-compiled `.po` change simply does nothing.

## 📡 Translating an API

For a JSON API, i18n means two distinct things — and only one is Django's job:

### 1. Translating **your** messages

Validation errors, DRF's own messages, status text. `LocaleMiddleware` plus `Accept-Language` handles it:

```http
GET /api/recipe/recipes/
Accept-Language: ar
```

```json
{"detail": "لم يتم توفير بيانات اعتماد المصادقة."}
```

DRF ships translations for its built-in messages. Yours need `gettext_lazy` in serializers:

```python
class RecipeSerializer(serializers.ModelSerializer):
    def validate_title(self, value):
        if len(value.strip()) < 3:
            raise serializers.ValidationError(_("Title must be at least 3 characters."))
        return value.strip()
```

### 2. Translating **user data**

Recipe titles, tag names. Django's i18n does **not** do this — it translates source strings, not database rows. You need either a per-language column, a translation table, or a package like `django-modeltranslation` / `django-parler`.

> [!TIP] Don't conflate the two
> "Translate my API" almost always means #1. #2 is a data-modelling decision with real cost, and most APIs correctly decide user content stays in the language it was written in.

## 🕐 Timezones

```python
USE_TZ = True
TIME_ZONE = "UTC"
```

**Store UTC. Always.** Convert at the edge.

```python
from django.utils import timezone

timezone.now()          # ✅ aware datetime in UTC
datetime.now()          # ❌ naive, server-local, unusable
```

```python
from zoneinfo import ZoneInfo

local = timezone.localtime(recipe.created_at, ZoneInfo("Africa/Algiers"))
```

DRF serializes `DateTimeField` as ISO 8601 with an offset:

```json
{"created_at": "2026-08-16T14:30:00Z"}
```

which is unambiguous — let the client localise it.

> [!CAUTION] `RuntimeWarning: DateTimeField received a naive datetime`
> Mixing naive and aware datetimes gives comparisons that are wrong rather than loud. Never `datetime.now()`; always `timezone.now()`.

## 🔄 RTL — for the Arabic edition

```django
<html lang="{{ LANGUAGE_CODE }}" dir="{% if LANGUAGE_BIDI %}rtl{% else %}ltr{% endif %}">
```

`LANGUAGE_BIDI` is `True` for Arabic, Hebrew, Persian and Urdu. The Django admin already uses it — set the language to `ar` and the admin flips direction on its own.

Relevant to [[AR/README|this vault's Arabic edition]]: prose runs RTL, but **code blocks must stay LTR**. Obsidian handles that automatically (Settings → Editor → RTL); in HTML you'd need `<pre dir="ltr">`.

## ⚠️ Gotchas

- **Translations not appearing** → forgot `compilemessages`, or `LOCALE_PATHS` is wrong, or `LocaleMiddleware` is missing/misordered.
- **Everyone sees one language** → `gettext` used where `gettext_lazy` was needed.
- **`makemessages` finds nothing** → strings not wrapped in `_()`, or `xgettext` isn't installed (`apk add gettext`).
- **Dates off by hours** → naive datetimes, or `USE_TZ = False`.
- **Arabic plurals wrong** → string concatenation instead of `ngettext`.
- **`.mo` files in git** → generate them at build time instead; they're binary and conflict badly.
