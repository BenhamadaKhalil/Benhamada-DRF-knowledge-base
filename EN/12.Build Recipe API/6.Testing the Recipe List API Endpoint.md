# 🧪 Testing the Recipe List API Endpoint

## 🎯 Core Concept

Before implementing the **Recipe API endpoint**, we first write **tests** to define the expected behavior.

This follows **Test Driven Development (TDD)**:

1. Write tests
2. Run tests → they fail
3. Implement feature
4. Tests pass

The tests verify that:

- 🔒 **Authentication is required**
- 📋 **Authenticated users can retrieve recipes**
- 👤 **Users only see their own recipes**

> [!INFO]
> Tests act as a **contract for how the API should behave** before the endpoint exists.

---

# 🏗️ Logic Flow

Testing the **Recipe List API** follows this flow:

```

Test Client  
↓  
API Request (GET /recipes/)  
↓  
Recipe View  
↓  
Database Query  
↓  
Serializer  
↓  
Response Data

```

In tests:

```

Test Case  
↓  
Create test data  
↓  
Call API endpoint  
↓  
Validate response status  
↓  
Validate response data

```

# 🔗 API URL Helper

Define the recipe endpoint URL:

```python
RECIPES_URL = reverse("recipe:recipe-list")
```

This generates the endpoint:

```
/api/recipe/recipes/
```

> [!TIP]  
> Using `reverse()` avoids hardcoding URLs.

# 🧩 Helper Function: Create Recipe

To avoid repeating code in tests, we create a **helper function**.

```python
def create_recipe(user, **params):
    """Create and return a sample recipe."""
    
    defaults = {
        "title": "Sample recipe title",
        "time_minutes": 22,
        "price": Decimal("5.25"),
        "description": "Sample description",
        "link": "http://example.com/recipe.pdf",
    }

    defaults.update(params)

    recipe = Recipe.objects.create(user=user, **defaults)

    return recipe
```

---

## 🔍 Why Use a Helper Function?

Without helper:

```python
Recipe.objects.create(
    title="Sample",
    time_minutes=10,
    price=Decimal("5.00"),
    user=user
)
```

Repeated **many times** across tests.

Helper simplifies:

```python
create_recipe(user)
```

or override fields:

```python
create_recipe(user, title="New Recipe")
```

> [!TIP]  
> `**params` allows **dynamic parameters** to override defaults.

# 🔓 Public API Tests (Unauthenticated)

These tests verify that **unauthenticated users cannot access the API**.

```python
class PublicRecipeApiTests(TestCase):
    """Test unauthenticated API requests"""

    def setUp(self):
        self.client = APIClient()

    def test_auth_required(self):
        """Test authentication is required"""
        res = self.client.get(RECIPES_URL)

        self.assertEqual(res.status_code, status.HTTP_401_UNAUTHORIZED)
```

### What This Test Does

```
Unauthenticated User
      ↓
GET /recipes/
      ↓
Response → 401 Unauthorized
```

> [!CAUTION]  
> Recipes are **private**, so users must authenticate.

---

# 🔐 Private API Tests (Authenticated)

These tests simulate **logged-in users**.

```python
class PrivateRecipeApiTests(TestCase):
    """Test authenticated API requests"""

    def setUp(self):
        self.client = APIClient()

        self.user = get_user_model().objects.create_user(
            email="user@example.com",
            password="testpass123",
        )

        self.client.force_authenticate(self.user)
```

### What Happens in `setUp`

```
Create User
     ↓
Authenticate API Client
     ↓
All requests run as this user
```

> [!TIP]  
> `force_authenticate()` bypasses login for testing.

# 📋 Test: Retrieve Recipe List

```python
def test_retrieve_recipes(self):
    """Test retrieving a list of recipes"""

    create_recipe(user=self.user)
    create_recipe(user=self.user)

    res = self.client.get(RECIPES_URL)

    recipes = Recipe.objects.all().order_by("-id")
    serializer = RecipeSerializer(recipes, many=True)

    self.assertEqual(res.status_code, status.HTTP_200_OK)
    self.assertEqual(res.data, serializer.data)
```

---

## 🧠 What This Test Verifies

1️⃣ Two recipes are created  
2️⃣ API request retrieves recipes  
3️⃣ Response status is **200 OK**  
4️⃣ Response data matches serialized database data

```
Database
  ├── Recipe 1
  └── Recipe 2

API Response
  ↓
Serialized Recipe List
```

---

# 📊 Why `many=True`?

```python
serializer = RecipeSerializer(recipes, many=True)
```

Because the serializer is receiving **multiple objects**.

|Scenario|many|
|---|---|
|Single object|False|
|List of objects|True|

# 👤 Test: Recipes Limited to Authenticated User

This test ensures users **only see their own recipes**.

```python
def test_recipe_list_limited_to_user(self):
    """Test list of recipes is limited to authenticated user"""

    other_user = get_user_model().objects.create_user(
        "other@example.com",
        "password123",
    )

    create_recipe(user=other_user)
    create_recipe(user=self.user)

    res = self.client.get(RECIPES_URL)

    recipes = Recipe.objects.filter(user=self.user)
    serializer = RecipeSerializer(recipes, many=True)

    self.assertEqual(res.status_code, status.HTTP_200_OK)
    self.assertEqual(res.data, serializer.data)
```

---

## 🔍 What This Test Checks

```
Database
 ├── Recipe (User A)
 └── Recipe (User B)

Authenticated as User B
      ↓
API Request
      ↓
Response returns ONLY:
 └── Recipe (User B)
```

If the API returned **both recipes**, the test would fail.

> [!CAUTION]  
> This protects **user data privacy**.

# ⚡ Pro-Tips & Shortcuts

> [!TIP]  
> Always separate API tests into:

```
Public API tests
Private API tests
```

This clearly tests **authentication behavior**.

---

> [!TIP]  
> Use helper functions like:

```
create_recipe()
create_user()
create_tag()
```

They make tests **clean and reusable**.

---

> [!TIP]  
> Always test:

- Status code
    
- Response structure
    
- Response data
    

---

> [!CAUTION]  
> Test failures are **expected in TDD** until the feature is implemented.

The serializer module does not yet exist, so tests will fail with:

```

```
