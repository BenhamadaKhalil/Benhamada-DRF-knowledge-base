## 🎣 Retrieving

```python
Recipe.objects.all()                          # QuerySet — lazy, no query yet
Recipe.objects.get(id=1)                      # one object or raises
Recipe.objects.filter(user=user)              # WHERE
Recipe.objects.exclude(price=0)               # WHERE NOT
Recipe.objects.first()  /  .last()            # LIMIT 1
Recipe.objects.count()                        # SELECT COUNT(*)
Recipe.objects.exists()                       # SELECT 1 … LIMIT 1
Recipe.objects.none()                         # empty QuerySet, no query
```

| `get()` raises | When |
| --- | --- |
| `Recipe.DoesNotExist` | no match |
| `Recipe.MultipleObjectsReturned` | more than one |

```python
from django.shortcuts import get_object_or_404
recipe = get_object_or_404(Recipe, id=1, user=request.user)     # → 404, not 500
```

> [!TIP] `exists()` beats `count()` beats `len()`
> ```python
> if Recipe.objects.filter(user=user).exists():   # ✅ LIMIT 1
> if Recipe.objects.filter(user=user).count():    # ⚠️ full COUNT
> if len(Recipe.objects.filter(user=user)):       # ❌ fetches every row into Python
> ```

## 🔎 Field lookups

| Lookup | SQL | Example |
| --- | --- | --- |
| `exact` | `=` | `filter(title__exact="Curry")` |
| `iexact` | `ILIKE` | `filter(email__iexact="A@B.com")` |
| `contains` / `icontains` | `LIKE '%x%'` | `filter(title__icontains="cur")` |
| `startswith` / `endswith` | `LIKE 'x%'` | `filter(title__startswith="C")` |
| `in` | `IN (…)` | `filter(id__in=[1, 2, 3])` |
| `gt` `gte` `lt` `lte` | `> >= < <=` | `filter(price__lte=10)` |
| `range` | `BETWEEN` | `filter(price__range=(5, 20))` |
| `isnull` | `IS NULL` | `filter(link__isnull=True)` |
| `regex` / `iregex` | `~` | `filter(title__regex=r"^C")` |
| `date` `year` `month` `day` | date parts | `filter(created__year=2026)` |

Traverse relations with `__`:

```python
Recipe.objects.filter(tags__name="Vegan")
Recipe.objects.filter(user__email__endswith="@example.com")
Tag.objects.filter(recipe__price__gt=10)          # reverse relation
```

> [!WARNING] Chained `filter()` on a multi-valued relation is not one `filter()`
> ```python
> # rows where ONE tag is both vegan and dessert — usually zero
> Recipe.objects.filter(tags__name="Vegan", tags__name="Dessert")
>
> # rows having a vegan tag AND (separately) a dessert tag — usually what you meant
> Recipe.objects.filter(tags__name="Vegan").filter(tags__name="Dessert")
> ```
> Each `.filter()` on a M2M creates its own JOIN. This distinction bites everyone once.

## 🔀 `Q` — OR, AND, NOT

```python
from django.db.models import Q

Recipe.objects.filter(Q(price__lt=5) | Q(time_minutes__lt=10))       # OR
Recipe.objects.filter(Q(price__lt=5) & Q(user=user))                 # AND
Recipe.objects.filter(~Q(link=""))                                   # NOT
Recipe.objects.filter(Q(title__icontains=q) | Q(description__icontains=q))
```

Build them dynamically:

```python
query = Q(user=request.user)
if search:
    query &= Q(title__icontains=search)
if max_price:
    query &= Q(price__lte=max_price)

Recipe.objects.filter(query)
```

## 🧮 `F` — reference a column in the query

```python
from django.db.models import F

# compare two columns
Recipe.objects.filter(price__gt=F("time_minutes"))

# atomic update — no read, no race
Recipe.objects.filter(id=1).update(views=F("views") + 1)

# bulk arithmetic across every row
Recipe.objects.update(price=F("price") * 1.1)
```

`F()` runs in the database. The read-modify-write version in Python loses updates under concurrency — see [[8.Transactions]].

## 📊 Aggregation and annotation

```python
from django.db.models import Count, Sum, Avg, Max, Min

# aggregate → one dict for the whole queryset
Recipe.objects.aggregate(Avg("price"), Max("time_minutes"), Count("id"))
# {'price__avg': 8.25, 'time_minutes__max': 120, 'id__count': 43}

# annotate → adds an attribute to EACH row
Recipe.objects.annotate(tag_count=Count("tags")).filter(tag_count__gte=2)

User.objects.annotate(recipe_count=Count("recipe")).order_by("-recipe_count")
```

Conditional aggregation:

```python
from django.db.models import Case, When, IntegerField

Recipe.objects.aggregate(
    cheap=Count(Case(When(price__lt=5, then=1), output_field=IntegerField())),
)
```

> [!WARNING] Double-counting with multiple annotations
> `annotate(Count("tags"), Count("ingredients"))` multiplies the JOINs and inflates both numbers. Use `distinct=True`:
> ```python
> .annotate(t=Count("tags", distinct=True), i=Count("ingredients", distinct=True))
> ```

## 🚀 Performance

```python
.select_related("user")                     # FK / OneToOne → JOIN
.prefetch_related("tags", "ingredients")    # M2M / reverse FK → second query
.only("id", "title")                        # fetch these columns only
.defer("description")                       # fetch everything except these
.values("id", "title")                      # dicts, not model instances
.values_list("id", flat=True)               # a flat list of ids
.distinct()                                 # SELECT DISTINCT
.iterator()                                 # stream — don't cache the whole result
```

Full treatment in [[4.The N+1 Problem]].

**Bulk operations** — one query instead of N:

```python
Recipe.objects.bulk_create([Recipe(...), Recipe(...)])
Recipe.objects.bulk_update(recipes, ["price"])
Recipe.objects.filter(price=0).update(price=1)        # no signals, no save()
Recipe.objects.filter(user=user).delete()
```

> [!CAUTION] Bulk methods skip `save()` and signals
> `update()` and `bulk_create()` do **not** call `Model.save()`, do **not** fire `post_save`, and do **not** run `auto_now`. If you rely on any of those, loop instead — or invalidate manually. See [[7.Signals]].

## 🔗 Relations

```python
recipe.tags.all()                 # forward M2M
recipe.tags.add(tag)              # link
recipe.tags.remove(tag)           # unlink
recipe.tags.set([t1, t2])         # replace the whole set
recipe.tags.clear()               # unlink all

tag.recipe_set.all()              # reverse FK/M2M — default name
# with related_name="recipes":
tag.recipes.all()
```

```python
obj, created = Tag.objects.get_or_create(user=user, name="Vegan")
obj, created = Tag.objects.update_or_create(
    user=user, name="Vegan", defaults={"name": "Vegan"}
)
```

`get_or_create` is the engine behind [[Nested Serialization|nested tag writes]].

## 📅 Dates and ordering

```python
from django.utils import timezone
from datetime import timedelta

Recipe.objects.filter(created__gte=timezone.now() - timedelta(days=7))
Recipe.objects.filter(created__date=timezone.now().date())

Recipe.objects.order_by("-created", "title")     # DESC then ASC
Recipe.objects.order_by("?")                     # random — slow on big tables
```

```python
from django.db.models.functions import TruncMonth

Recipe.objects.annotate(month=TruncMonth("created")) \
              .values("month") \
              .annotate(n=Count("id")) \
              .order_by("month")
```

## ⏳ Laziness — when the query actually runs

QuerySets don't hit the database until you force them:

| Doesn't run a query | Runs a query |
| --- | --- |
| `qs = Recipe.objects.all()` | `list(qs)` |
| `qs = qs.filter(...)` | `for r in qs:` |
| `qs = qs.order_by(...)` | `len(qs)` |
| `qs2 = qs[5:10]` | `bool(qs)` / `if qs:` |
| | `qs[0]` |
| | `repr(qs)` — **which is why printing in a shell "works"** |

```python
qs = Recipe.objects.filter(user=user)      # 0 queries
qs = qs.filter(price__lt=10)               # 0 queries
qs = qs.order_by("-id")                    # 0 queries
results = list(qs)                         # 1 query — everything at once
```

Chain freely; it costs nothing until evaluation.

> [!TIP] Re-evaluating is a fresh query
> ```python
> for r in qs: ...     # query 1
> for r in qs: ...     # cached — same QuerySet object
> for r in Recipe.objects.filter(...): ...   # a NEW QuerySet → new query
> ```

## ⚠️ Gotchas

- **`filter(x=1, y=2)` vs `.filter(x=1).filter(y=2)`** on M2M — different results.
- **Slicing then filtering** → `TypeError: Cannot filter a query once a slice has been taken.` Filter first.
- **`order_by()` with no argument** clears ordering; `order_by("?")` is a full random sort.
- **`.distinct()` with `order_by` on a related field** can produce surprising duplicates in Postgres.
- **`update()` returns the row count**, not objects.
- **Comparing a QuerySet to a list** in a test → wrap it: `list(qs)`.
