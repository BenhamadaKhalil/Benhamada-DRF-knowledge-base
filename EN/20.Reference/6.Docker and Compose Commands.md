# 🐳 Docker and Compose Commands

> The pattern for everything in this project:
> `docker compose run --rm app sh -c "<the django command>"`

---

## 🔑 The one-liner, explained

| Part | Why |
| --- | --- |
| `docker compose` | v2 syntax (space, not hyphen). `docker-compose` is the old v1 binary |
| `run` | start a **one-off** container for this command |
| `--rm` | delete the container afterwards — without it they accumulate forever |
| `app` | the service name from `docker-compose.yml` |
| `sh -c "…"` | run the whole quoted string as one shell command, so `&&` works |

```bash
docker compose run --rm app sh -c "python manage.py test && flake8"
```

Without `sh -c`, only `python` is the command and `&& flake8` is passed to Django as arguments.

## ▶️ Day to day

```bash
docker compose up
```

```bash
docker compose up -d
```

```bash
docker compose down
```

```bash
docker compose logs -f app
```

```bash
docker compose ps
```

```bash
docker compose restart app
```

| Command | Does |
| --- | --- |
| `up` | build if needed, create, start, attach to logs |
| `up -d` | same, detached |
| `up --build` | force a rebuild first |
| `down` | stop and remove containers + network |
| `down -v` | **also deletes named volumes — destroys your database** |
| `stop` | stop without removing |
| `logs -f app` | follow one service's logs |
| `exec app sh` | shell inside a **running** container |
| `run --rm app sh` | shell in a **new throwaway** container |

> [!CAUTION] `down -v` deletes your data
> The `-v` flag removes named volumes, including `dev-db-data`. That is your entire local database. It's the right command when you *want* a clean slate (see the `InconsistentMigrationHistory` fix), and a disaster otherwise.

## 🏗️ Building

```bash
docker compose build
```

```bash
docker compose build --no-cache
```

```bash
docker compose build --build-arg DEV=true
```

```bash
docker compose -f docker-compose-deploy.yml build app
```

> [!TIP] Layer caching is why order matters in the Dockerfile
> `COPY requirements.txt` → `RUN pip install` → `COPY ./app` means a code change reuses the cached dependency layer. Copy the app first and every edit reinstalls every package. See [[5.Dockerfile]].

## 🗄️ Database access

```bash
docker compose exec db psql -U devuser -d devdb
```

```bash
docker compose exec db pg_dump -U devuser devdb > backup.sql
```

```bash
docker compose exec -T db psql -U devuser -d devdb < backup.sql
```

Useful `psql` once you're in:

| Command | Shows |
| --- | --- |
| `\dt` | tables |
| `\d core_recipe` | one table's columns and indexes |
| `\du` | users/roles |
| `\l` | databases |
| `\q` | quit |

## 🧹 Cleaning up

```bash
docker system df
```

```bash
docker image prune -a
```

```bash
docker container prune
```

```bash
docker system prune -a
```

> [!CAUTION] Read the flags before you run prune
> `docker system prune -a --volumes` deletes **every** unused image, container, network **and volume** on the machine — including databases from other projects. `-a` alone is usually what you want.

## 🔍 Debugging

```bash
docker compose logs --tail=100 app
```

```bash
docker compose exec app sh
```

```bash
docker compose run --rm app sh -c "env"
```

```bash
docker compose top
```

```bash
docker stats
```

```bash
docker compose exec app sh -c "ls -la /vol/web/static"
```

| Symptom | First command |
| --- | --- |
| container exits immediately | `docker compose logs app` |
| "connection refused" to db | `docker compose ps` — is `db` up? |
| env var seems empty | `docker compose config` |
| static files 404 | `exec app sh -c "ls /vol/web/static"` |
| code changes ignored | check the volume mount in `docker-compose.yml` |
| out of disk | `docker system df` |

## 📄 The compose file, annotated

```yaml
services:
  app:
    build:
      context: .              # Dockerfile location
      args:
        - DEV=true            # → the ARG in the Dockerfile
    ports:
      - "8000:8000"           # host:container
    volumes:
      - ./app:/app            # live reload — DEV ONLY
    command: >
      sh -c "python manage.py wait_for_db &&
             python manage.py migrate &&
             python manage.py runserver 0.0.0.0:8000"
    environment:
      - DB_HOST=db            # the SERVICE NAME resolves via Docker DNS
      - DB_NAME=devdb
    depends_on:
      - db                    # start order only — NOT readiness

  db:
    image: postgres:16-alpine    # Django 6.1 requires PostgreSQL 15+
    volumes:
      - dev-db-data:/var/lib/postgresql/data
    environment:
      - POSTGRES_DB=devdb

volumes:
  dev-db-data:
```

Two things worth internalising:

- **`0.0.0.0:8000`, not `127.0.0.1:8000`.** Binding to localhost inside a container means only the container can reach it, and your port mapping does nothing.
- **`depends_on` is start order, not readiness.** The `db` container being "started" doesn't mean Postgres is accepting connections. That gap is precisely why [[8.Create wait_for_db|wait_for_db]] exists.
