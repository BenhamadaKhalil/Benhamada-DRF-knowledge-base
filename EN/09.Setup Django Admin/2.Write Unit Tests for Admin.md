# Django Admin – TDD: Write Unit Tests for Admin (Users List)

## 🎯 Main Goal

Start customizing Django Admin using **Test Driven Development (TDD)** by first writing tests that verify:

- The **Users list page** in Django Admin exists
    
- It displays the **user’s name** and **email**
    

---

## 📁 Create a New Test File

Inside your core app tests folder, create:

`core/tests/test_admin.py`

Add a module docstring:

- “Tests for Django admin modifications”
    

---

## 📦 Imports Used

In `test_admin.py`, the test file uses:

- `TestCase` → Django testing base class
    
- `get_user_model()` → access the active user model (custom or default)
    
- `reverse()` → generate URLs by name (instead of hardcoding)
    
- `Client` → Django test client to simulate HTTP requests
    

Typical setup:

```python
from django.test import TestCase
from django.contrib.auth import get_user_model
from django.urls import reverse
from django.test import Client
```

## 🧪 Test Class Structure

Create a test class that inherits from `TestCase`:

- Name example: `AdminSiteTests`
    
- Add docstring: “Tests for Django admin”
    

```python
class AdminSiteTests(TestCase):
    """Tests for django admin."""
```

## ⚙️ The `setUp()` Method (Runs Before Every Test)

### Why `setUp()`?

In Django/`unittest`, `setUp()` is a special method that runs automatically **before each test** in the class.

⚠️ Important: it must be written as `setUp` (camelCase) — not `setup` — otherwise it won’t run.

### What happens inside `setUp()`?

You prepare everything needed for tests:

1. Create a Django test client
    
2. Create an admin/superuser
    
3. Force-login the client as admin
    
4. Create a normal user to verify it appears in admin list
    

Key idea: every request made with `self.client` will behave as if it’s made by the logged-in admin user.

Example logic:

```python
def setUp(self):
    self.client = Client()

    self.admin_user = get_user_model().objects.create_superuser(
        email='admin@example.com',
        password='testpass123',
    )
    self.client.force_login(self.admin_user)

    self.user = get_user_model().objects.create_user(
        email='user@example.com',
        password='testpass123',
        name='Test User',
    )
```

## ✅ Test: Users Are Listed on Admin Page

### What we are testing

We want to test the Django Admin “change list” page for users.

This page should show users in a list/table.

### Step 1 — Build the URL with `reverse()`

Django admin uses predictable URL naming patterns.

This pattern:

- `admin:<app_label>_<model_name>_changelist`
    

In the video example:

- `admin:core_user_changelist`
    

So:

```python
url = reverse('admin:core_user_changelist')
```

### Step 2 — Request the page

```python
res = self.client.get(url)
```

Because of `force_login`, this request is authenticated as the admin.

### Step 3 — Assert the user appears

We check that the page contains:

- the user name
    
- the user email
    

```python
self.assertContains(res, self.user.name)
self.assertContains(res, self.user.email)
```

### Full test example

```python
def test_users_listed(self):
    """Test that users are listed on user page."""
    url = reverse('admin:core_user_changelist')
    res = self.client.get(url)

    self.assertContains(res, self.user.name)
    self.assertContains(res, self.user.email)
```

---

## 🧠 Why This Test Might Fail Right Now (Expected)

When you run the test at this stage, it may fail with something like:

- `NoReverseMatch`
    

Meaning Django can’t find the admin URL name you asked for.

That usually happens because:

- The User model is not registered in the admin yet
    
- Or admin customization not implemented yet
    

✅ This is normal in TDD:  
You write the test first → it fails → then you implement code to make it pass.

## ▶️ Running Tests (Docker)

The course runs tests through docker-compose, something like:

```bash
docker compose run --rm app sh -c "python manage.py test"
```

Expected result: tests fail **for now**, because admin registration/customization hasn’t been done yet.

---

## 🔑 Key Takeaways

- Use TDD: write tests before implementing admin changes
    
- `setUp()` runs before every test and prepares client + data
    
- `Client().force_login(user)` makes requests authenticated
    
- Django Admin URLs follow predictable patterns like:
    
    - `admin:app_model_changelist`
        
- Initial failure (`NoReverseMatch`) is expected until admin registration is done
