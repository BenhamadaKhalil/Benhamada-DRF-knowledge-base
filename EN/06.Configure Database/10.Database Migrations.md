# Django – Database Migrations + ORM (What & Why)

## 📌 Lesson Goal
Now that `wait_for_db` works, the next step is making sure our database schema exists and stays up-to-date using **migrations**.

This lesson explains:
- what Django ORM is
- what migrations are
- how models → tables
- the commands: `makemigrations` and `migrate`
- why we run migrations after `wait_for_db`

---

# 🧠 Django ORM (Object Relational Mapper)

Django includes an **ORM** (Object Relational Mapper).

### What it does
ORM is an abstraction layer between:
- your **Python code** (models)
- your **SQL database** (Postgres, MySQL, etc.)

Instead of writing raw SQL manually, Django handles:
- table creation
- columns changes
- inserts / updates / deletes
- schema changes over time

✅ You focus on Python code, Django handles SQL.

---

# ✅ Why This Is Useful

In many other stacks (example: PHP + SQL):
- you write SQL queries yourself
- you manually create/alter tables
- you manually add/remove columns

With Django:
- you define models
- Django generates migrations automatically
- Django applies changes automatically

This is one of Django’s biggest strengths.

---

# 🔁 Database Flexibility

Because Django uses the ORM:
- You can switch databases (within reason)

Example:
- Postgres → MySQL

Usually requires:
- changing DB engine config
- changing dependencies

⚠️ But if you rely on DB-specific features (like advanced Postgres features), switching becomes harder.

---

# 🧱 Models → Tables

A **model** (Python class) usually maps to:
- a **table** in the database

A model contains:
- a name (class name)
- fields (database columns)
- relationships (foreign keys, etc.)
- optional custom logic (methods/validation)

---

## Example Model (Ingredient)

Conceptually:

- Model name: `Ingredient` → table `ingredient`
- Fields:
  - `name` (text field, max length 255)
  - `user` (ForeignKey to User)
- Relationship behavior:
  - `on_delete=models.CASCADE` → delete ingredient if user is deleted

---

# 📦 What Are Migrations?

A migration is:
- an **auto-generated Python file**
- that represents a database change

You usually don’t write migrations manually (99% of the time).
Django creates them by comparing:
- your current models
- existing migration history

---

# 🛠️ Migration Commands

## 1) Create migration files
```bash
python manage.py makemigrations
```

What it does:
- checks your models
- generates new migration files if changes exist
- first time → creates initial migration

✅ Works only if the app is enabled in `INSTALLED_APPS`.

---

## 2) Apply migrations to database
```bash
python manage.py migrate
```

What it does:
- reads migration files
- applies changes to the database
- if already applied → skips safely

✅ Safe to run repeatedly.

---

# 🧩 Best Practice Startup Flow (Docker)

Because DB might not be ready instantly, best practice is:

1) wait for DB  
2) run migrations  
3) start the app

Conceptually:

```bash
python manage.py wait_for_db
python manage.py migrate
python manage.py runserver
```

This ensures:
- DB is reachable
- schema is correct
- your app starts reliably

---

# 🔥 Key Takeaways
- Django ORM handles database structure + queries through Python models
- Models map to DB tables
- Migrations are auto-generated Python files describing schema changes
- `makemigrations` creates migration files
- `migrate` applies them to the database
- In Docker: run `wait_for_db` then `migrate` before starting the app
