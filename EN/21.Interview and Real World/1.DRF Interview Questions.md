## 🟢 Fundamentals

### What is Django REST Framework, and what does it add to Django?

Django gives you the ORM, URL routing, and an admin. DRF adds the API layer on top: **serializers** (model ↔ JSON with validation), **class-based API views** and ViewSets, pluggable **authentication and permissions**, **content negotiation**, throttling, pagination, and a browsable API. You can build an API in plain Django — you just end up rewriting all of that by hand.

### Serializer vs ModelSerializer?

`Serializer` is fully manual: declare every field, write `create()` and `update()`. `ModelSerializer` infers fields from the model and gives you both methods for free. Use `ModelSerializer` when the payload maps to a model; use `Serializer` when it doesn't — a login payload, a report request, a webhook body.

### APIView vs ViewSet? ⭐

`APIView` maps one URL to one class, and you write `get()` / `post()` yourself. A `ViewSet` groups the *actions* for a resource — `list`, `retrieve`, `create`, `update`, `destroy` — and a router generates the URLs.

**Choosing:** standard CRUD on a model → `ModelViewSet`. A single non-CRUD endpoint (`/token/`, `/export/`, a webhook receiver) → `APIView`. Forcing an odd endpoint into a ViewSet costs more than it saves.

### What does `perform_create` do, and why not override `create`?

`perform_create(serializer)` runs after validation, just before saving — the hook for injecting server-side data:

```python
def perform_create(self, serializer):
    serializer.save(user=self.request.user)
```

Overriding `create()` means reimplementing validation, the response, and the status code. `perform_create` changes only the part you need.

**Why it matters:** taking `user` from the token rather than the payload is what stops a client from creating rows owned by someone else — mass assignment.

## 🟡 Intermediate

### How do you stop a user reading another user's data? ⭐

Filter the queryset:

```python
def get_queryset(self):
    return self.queryset.filter(user=self.request.user)
```

**The key insight:** `has_object_permission()` is **never called on list endpoints** — DRF has no single object to check. If your only protection is an object-level permission class, `GET /recipes/` returns everything in the database.

Queryset filtering also yields `404` instead of `403` for another user's object, which is better: a `403` confirms the row exists, letting an attacker enumerate your IDs.

### `queryset` attribute vs `get_queryset()` method?

The class attribute is evaluated once at import and is what the router uses to infer the URL basename. The method runs per request and is what actually decides what the caller sees. Setting only the attribute and forgetting the method is how every user ends up seeing every row.

### Why doesn't `ModelSerializer` support writable nested fields? ⭐

Because the intent is ambiguous. Given `{"tags": [{"name": "vegan"}]}`, DRF can't know whether you mean create a new tag, find an existing one, or error on a duplicate — and getting it wrong silently corrupts data. So it refuses and makes you write `create()`:

```python
def create(self, validated_data):
    tags = validated_data.pop("tags", [])
    recipe = Recipe.objects.create(**validated_data)
    auth_user = self.context["request"].user
    for tag in tags:
        tag_obj, _ = Tag.objects.get_or_create(user=auth_user, **tag)
        recipe.tags.add(tag_obj)
    return recipe
```

`get_or_create` is the decision the framework wouldn't make for you.

### `write_only` vs `read_only`?

`write_only` — accepted on input, never returned. Passwords.
`read_only` — returned on output, ignored on input. IDs, timestamps.

```python
extra_kwargs = {"password": {"write_only": True, "min_length": 5}}
```

### Authentication vs authorization?

Authentication = *who are you* (`TokenAuthentication` sets `request.user`). Authorization = *are you allowed* (permission classes). Authentication runs first; a `401` means we don't know you, a `403` means we do and the answer is no.

### Why token auth over sessions for an API?

Sessions rely on cookies, which means CSRF protection and cross-domain pain, and they're awkward for mobile clients. Token auth sends an explicit `Authorization` header — no CSRF surface, works identically from a browser, a phone, or `curl`.

### What is the N+1 problem and how do you fix it? ⭐

Serializing a list with nested relations issues one query for the list and one per row for the relations — 100 recipes with tags is 201 queries. Fix:

```python
.select_related("user")                    # FK / OneToOne → JOIN
.prefetch_related("tags", "ingredients")   # M2M / reverse FK → second query
```

**Detect it** with `assertNumQueries` in a test, or django-debug-toolbar in dev. **Why not one JOIN for M2M:** joining 100 recipes to 5 tags each returns 500 rows to reconstruct 100 objects — the row multiplication costs more than a second query.

## 🔴 Senior

### Walk me through what happens on `POST /api/recipes/`. ⭐

1. URL router matches the path to the viewset action
2. Django middleware (CORS, session)
3. `APIView.dispatch()` wraps the request
4. **Authentication** — `TokenAuthentication` reads the header, sets `request.user`; fails → `401`
5. **Permissions** and **throttling**; fail → `403` / `429`
6. The `create` action runs → `perform_create`
7. **Serializer** validates; fails → `400`. Then `create()` writes
8. ORM → SQL → Postgres
9. Renderer serialises the response → `201`

Any `APIException` short-circuits to DRF's exception handler.

**The point of knowing this** is debugging: 401/403 is step 4–5, 400 is step 7, 404 is step 1 or `get_queryset()`, slow is step 8.

### When would you choose JWT over DRF's token auth? ⭐

When multiple services must verify the same identity without calling a shared auth service — the stateless verification is genuinely worth something there.

**What you give up:** revocation. A stolen JWT works until it expires. Adding a denylist to fix that reintroduces the database lookup you chose JWT to avoid.

For a single Django service, one indexed primary-key lookup per request is well under a millisecond. I'd use DRF tokens with an expiry class, and reach for JWT when I could name the specific problem it solved.

### What's wrong with this?

```python
with transaction.atomic():
    recipe = Recipe.objects.create(**data)
    process_recipe.delay(recipe.id)
```

The Celery worker can pick up the task **before the transaction commits**, query for `recipe.id`, and get `DoesNotExist`. It's intermittent, never reproduces locally, and is constant under production load.

```python
transaction.on_commit(lambda: process_recipe.delay(recipe.id))
```

The same applies to emails, webhooks, and cache invalidation — anything the database cannot roll back belongs in `on_commit`.

### When would you *not* use a signal?

When I own the code that triggers the event. If `RecipeSerializer.create()` should send an email, I call `send_email()` there. A signal makes that invisible: to know what happens on recipe creation you have to grep the codebase for `post_save`.

Signals earn their keep when you *don't* own the sender — reacting to `django.contrib.auth`'s `User.save()` — or for genuinely cross-cutting concerns like audit logging.

**The trap:** signals don't fire on `bulk_create` or `QuerySet.update()`, so signal-based cache invalidation silently stops working the day someone writes a bulk update.

### How would you add pagination to a live API?

It's a **breaking change** — the response goes from a bare list to `{count, next, previous, results}`, so every client iterating the response breaks.

With clients I control, I'd coordinate the deploy. With clients I don't, I'd version the endpoint or gate the envelope behind a query parameter during a migration window, log usage of the unpaginated form, and remove it when that reaches zero.

I'd also pick the style deliberately: `PageNumberPagination` for a UI with page numbers, `CursorPagination` for infinite scroll or large tables — `?page=5000` becomes `OFFSET 49990`, which makes Postgres fetch and discard 49,990 rows.

### How do you know your API is healthy in production?

Three separate questions:

- **Is it up?** — uptime monitoring against a real health endpoint that checks the database, not against `/`
- **Did something break?** — Sentry, with `release=GIT_SHA` so I know which deploy introduced an error
- **What happened at 03:14?** — structured JSON logs to stdout with a request ID propagated through, and returned in the response header so a user can quote it

I'd also log 4xx, not just 5xx. A spike in 401s means someone is probing; a spike in 400s means a client shipped a bad release.

## 🧩 Live coding: things they might ask you to write

**"Only the owner can edit"**
```python
class IsOwner(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):
        return obj.user == request.user
```

**"A different serializer for list vs detail"**
```python
def get_serializer_class(self):
    if self.action == "list":
        return RecipeSerializer
    return RecipeDetailSerializer
```

**"A custom endpoint on a ViewSet"**
```python
@action(methods=["POST"], detail=True, url_path="upload-image")
def upload_image(self, request, pk=None):
    recipe = self.get_object()
    serializer = self.get_serializer(recipe, data=request.data)
    serializer.is_valid(raise_exception=True)
    serializer.save()
    return Response(serializer.data, status=status.HTTP_200_OK)
```

**"Validate that two fields agree"**
```python
def validate(self, attrs):
    if attrs["password"] != attrs["password_confirm"]:
        raise serializers.ValidationError({"password_confirm": "Passwords do not match."})
    return attrs
```

**"Test that a user can't read another user's data"**
```python
def test_cannot_read_other_users_recipe(self):
    other = create_user(email="other@example.com")
    recipe = create_recipe(user=other)

    res = self.client.get(detail_url(recipe.id))

    self.assertEqual(res.status_code, status.HTTP_404_NOT_FOUND)
```

## 🔄 Turn it around

Interviews are two-way. Good questions to ask:

- "How do you handle database migrations on deploy — is there downtime?"
- "What's your test coverage story, and does CI block a merge?"
- "How do you find out about a production error?"
- "Where does business logic live here — views, serializers, or a service layer?"
- "What's the oldest API version you still support?"

Each of these signals that you've thought about the things this section covers.
