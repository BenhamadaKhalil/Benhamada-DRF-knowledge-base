# 📐 Architecture Decision Records

> Six months from now, someone — probably you — will look at a decision in this codebase and think *"why on earth did we do that?"* An ADR is the answer, written while you still remember.

---

## 🎯 What an ADR is

A short markdown file recording **one** significant decision: the context, the options, the choice, and the consequences. Written once, never edited — if the decision changes, you write a new ADR that supersedes it.

```text
docs/adr/
├── 0001-use-postgresql.md
├── 0002-custom-user-model-with-email.md
├── 0003-token-authentication.md
└── 0004-nested-writes-via-get-or-create.md
```

> [!TIP] Why immutable
> An ADR is a record of what you knew and believed *at that moment*. Editing it destroys the only thing that makes it valuable — the ability to see whether the reasoning was sound given what was known. Supersede, don't rewrite.

---

## 📋 The template

```markdown
# ADR-000N: <Short title in the imperative>

- **Status:** Proposed | Accepted | Deprecated | Superseded by ADR-000M
- **Date:** YYYY-MM-DD
- **Deciders:** who was in the room

## Context

What forces are at play? What constraints exist? What did we know?
State facts, not conclusions.

## Options considered

### Option A — <name>
- ✅ pro
- ❌ con

### Option B — <name>
- ✅ pro
- ❌ con

## Decision

We chose **X**, because <the reason that actually decided it>.

## Consequences

**We accept:**
- what this costs us

**We gain:**
- what this buys us

**We will revisit if:**
- the concrete signal that would change this decision
```

That last line — **the trigger to revisit** — is the one most people leave out and the one that makes an ADR useful later.

## 📄 Worked example: ADR-0003

```markdown
# ADR-0003: Use DRF TokenAuthentication

- **Status:** Accepted
- **Date:** 2026-02-23

## Context

The API serves a mobile client and a web SPA on a different origin from
the API. We are a single Django service with no plans for additional
backend services. Expected load is under 100 requests/second.

Auth must work identically from a phone, a browser, and curl.

## Options considered

### Session authentication
- ✅ Built in; httpOnly cookie is the most XSS-resistant option
- ✅ Already needed for the Django admin
- ❌ Cross-origin cookies require CORS + SameSite configuration
- ❌ CSRF protection needed on every unsafe method
- ❌ Awkward for a mobile client

### DRF TokenAuthentication
- ✅ Built in, no dependency
- ✅ Explicit header — identical from every client type
- ✅ Instant revocation: delete the row
- ❌ One database lookup per request
- ❌ Default tokens never expire

### JWT (simplejwt)
- ✅ No database lookup
- ✅ Carries claims
- ❌ Cannot revoke before expiry without a denylist — which reintroduces
     the database lookup
- ❌ Extra dependency, refresh-token flow in every client
- ❌ Solves a scaling problem we do not have

## Decision

We chose **DRF TokenAuthentication**, plus a custom
`ExpiringTokenAuthentication` class giving tokens a 7-day lifetime.

The deciding factor is revocation. We need to be able to cut off a
compromised client immediately, and JWT cannot do that without giving
back its only advantage. The per-request lookup is an indexed primary-key
read — well under a millisecond, and not close to our bottleneck.

## Consequences

**We accept:**
- One DB read per authenticated request
- Clients must handle a 401 by re-authenticating after 7 days
- Sessions remain enabled for /admin and the browsable API

**We gain:**
- Instant revocation
- No new dependency
- One auth path for mobile, web, and CLI

**We will revisit if:**
- We split into more than one backend service, or
- Auth lookups appear in the top 3 of our slow-query log
```

## 🎯 What deserves an ADR

| Write one | Don't bother |
| --- | --- |
| Database choice (Postgres over MySQL) | variable names |
| Custom user model, and keying on email | which utility library to import |
| Auth scheme | code formatting |
| Pagination style | anything a linter decides |
| Nested writes vs separate endpoints | reversible in an afternoon |
| Sync vs background processing | |
| Deployment target | |
| A dependency you'd struggle to remove | |

**The test:** would reversing this decision take more than a day, or would a newcomer reasonably ask "why is it like this?" If yes, write it down.

## 🗣️ Why this matters in an interview

The most common senior-level question is some form of *"why did you build it that way?"*

A candidate who says **"that's how the tutorial did it"** has demonstrated they can follow instructions. A candidate who says:

> *"Token auth, because we needed instant revocation for a compromised mobile client. JWT would have removed the per-request lookup, but a denylist would have put it straight back — so the only real advantage was gone. We wrote it down as ADR-0003 with a revisit trigger: if we split into multiple services, or if auth shows up in our slow-query log."*

…has demonstrated they can make and defend an engineering decision. That's the difference the title is measuring.

> [!TIP] Write ADRs even for solo projects
> Especially for solo projects. There is nobody else to remember, and *"why did I do this?"* is a question you will genuinely ask yourself. It also gives you something concrete and unusual to show.
