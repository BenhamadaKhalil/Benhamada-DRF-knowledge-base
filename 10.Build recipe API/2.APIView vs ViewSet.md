# ⚔️ Django REST Framework — APIView vs ViewSet

## 🎯 Core Concept

When building APIs with **Django REST Framework (DRF)**, there are two major ways to handle requests:

- **APIView**
- **ViewSet**

Both are **base classes used to process HTTP requests**, but they are designed for **different types of APIs**.

> [!INFO]
> Choosing between **APIView** and **ViewSet** depends on whether your API is:
> - **Custom logic / non-CRUD → APIView**
> - **Standard CRUD operations → ViewSet**

---

# 🏗️ Logic Flow

### Standard Request Flow in DRF

```

Client Request  
↓  
URL  
↓  
View (APIView / ViewSet)  
↓  
Serializer  
↓  
Model  
↓  
Database  
↓  
JSON Response

````

The **View layer** is where the difference between **APIView** and **ViewSet** appears.

---

# 🔹 What is a View in Django?

In **Django**, a **View** is the code responsible for handling a request sent to a URL.

Traditional Django uses **function-based views**.

Example:

```python
def my_view(request):
    return HttpResponse("Hello")
````

However, **Django REST Framework extends this concept** by using **class-based views**, which provide:

- reusable logic
    
- built-in API tools
    
- extensibility
    

---

# 🔹 APIView

## 📌 Definition

`APIView` is a **class-based view** in DRF that handles **HTTP methods directly**.

Each HTTP method corresponds to a **method in the class**.

### Example Structure

```python
from rest_framework.views import APIView
from rest_framework.response import Response

class ExampleAPIView(APIView):

    def get(self, request):
        return Response({"message": "GET request"})

    def post(self, request):
        return Response({"message": "POST request"})
```

### Supported Methods

|HTTP Method|Class Method|
|---|---|
|GET|`get()`|
|POST|`post()`|
|PUT|`put()`|
|PATCH|`patch()`|
|DELETE|`delete()`|

---

## 🧠 When to Use APIView

APIView is best for **custom or non-CRUD APIs**.

Examples:

- 🔐 Authentication endpoints
    
- ⚙️ Triggering background jobs
    
- 🌍 Calling external APIs
    
- 🧮 Running calculations
    
- 📊 Custom business logic
    

Example:

```
POST /api/login/
POST /api/run-report/
POST /api/process-payment/
```

These endpoints **do not directly map to a database model**.

> [!INFO]  
> APIViews give **maximum flexibility** over:
> 
> - URL structure
>     
> - request processing logic
>     

---

# 🔹 ViewSets

## 📌 Definition

A **ViewSet** organizes API logic around **actions instead of HTTP methods**.

Instead of defining `get()` or `post()`, you define **actions** such as:

- `list`
    
- `retrieve`
    
- `create`
    
- `update`
    
- `partial_update`
    
- `destroy`
    

---

### Example ViewSet

```python
from rest_framework.viewsets import ModelViewSet
from .models import Recipe
from .serializers import RecipeSerializer


class RecipeViewSet(ModelViewSet):
    serializer_class = RecipeSerializer
    queryset = Recipe.objects.all()
```

> [!CODE]  
> `ModelViewSet` automatically provides **full CRUD functionality**.

---

## 📌 ViewSet Actions

|Action|HTTP Method|Purpose|
|---|---|---|
|`list`|GET|Get all objects|
|`retrieve`|GET|Get single object|
|`create`|POST|Create object|
|`update`|PUT|Full update|
|`partial_update`|PATCH|Partial update|
|`destroy`|DELETE|Delete object|

---

# ⚙️ Automatic URL Routing

One major advantage of **ViewSets** is the use of **Routers**.

Routers **automatically generate API URLs**.

Example:

```python
from rest_framework.routers import DefaultRouter
from .views import RecipeViewSet

router = DefaultRouter()
router.register("recipes", RecipeViewSet)

urlpatterns = router.urls
```

This automatically creates:

```
GET     /recipes/
POST    /recipes/
GET     /recipes/{id}/
PUT     /recipes/{id}/
PATCH   /recipes/{id}/
DELETE  /recipes/{id}/
```

> [!INFO]  
> No need to manually write URL patterns.

---

# ⚖️ APIView vs ViewSet Comparison

|Feature|APIView|ViewSet|
|---|---|---|
|Focus|HTTP Methods|Actions|
|Flexibility|High|Medium|
|Boilerplate|More code|Less code|
|URL routing|Manual|Automatic with Routers|
|Best for|Custom APIs|CRUD APIs|

---

# 🧠 Practical Rule

Use **APIView** when:

- API does **not map to a model**
    
- Logic is **custom or complex**
    

Use **ViewSet** when:

- API performs **CRUD operations**
    
- API maps **directly to a model**
    

---

# 💻 Example Comparison

### APIView Example

```python
class LoginAPIView(APIView):

    def post(self, request):
        # custom authentication logic
        pass
```

---

### ViewSet Example

```python
class RecipeViewSet(ModelViewSet):

    queryset = Recipe.objects.all()
    serializer_class = RecipeSerializer
```

---

# ⚡ Pro-Tips & Shortcuts

> [!INFO]  
> In **real-world DRF projects**, most APIs are built using:
> 
> **ModelViewSet + Routers**

This dramatically reduces boilerplate.

---

> [!CAUTION]  
> Avoid using ViewSets if your endpoint does **not map to a model**.

Example bad use case:

```
POST /api/send-email/
```

Better implemented with **APIView**.

---

> [!INFO]  
> DRF also supports **function-based views** using decorators:

```python
@api_view(["GET"])
def example(request):
    return Response({"message": "hello"})
```

However, large projects typically prefer **class-based views**.
