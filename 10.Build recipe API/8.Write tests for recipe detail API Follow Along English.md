# 1️⃣ What new feature are we adding?

Previously you had this endpoint:

```
GET /api/recipe/recipes/
```

Returns **all recipes**:

```json
[
  {"id":1,"title":"Pizza"},
  {"id":2,"title":"Burger"}
]
```

Now we add the **detail endpoint**:

```
GET /api/recipe/recipes/1/
```

Returns **one recipe**:

```json
{
  "id":1,
  "title":"Pizza",
  "time_minutes":30,
  "price":"10.00",
  "link":"http://example.com"
}
```

# 2️⃣ Why create a new serializer?

The instructor created **two serializers**.

### 1️⃣ List serializer

Used for the recipe list page.

```
GET /recipes
```

Example:

```json
{
"id":1,
"title":"Pizza"
}
```

Minimal fields → faster.

---

### 2️⃣ Detail serializer

Used when opening one recipe.

```
GET /recipes/1
```

Example:

```json
{
"id":1,
"title":"Pizza",
"time_minutes":30,
"price":"10.00",
"link":"http://..."
}
```

More fields → more information.

---

### Why separate them?

Real apps do this to **improve performance**.

Example:

Instagram feed:

```
GET /posts
```

Returns:

```
image
title
likes
```

But when you open the post:

```
GET /posts/15
```

Returns:

```
image
title
likes
comments
tags
description
```

# 3️⃣ The new helper function

They added:

```python
def detail_url(recipe_id):
    return reverse('recipe:recipe-detail', args=[recipe_id])
```

### Why a function?

Because the URL changes depending on the recipe.

Example URLs:

```
/api/recipe/recipes/1/
/api/recipe/recipes/2/
/api/recipe/recipes/3/
```

So the function builds it dynamically.

Example:

```python
detail_url(5)
```

returns

```
/api/recipe/recipes/5/
```

# 6️⃣ The architecture now

Your API structure is becoming:

```
Recipe Model
      │
      ▼
Serializers
   │        │
   ▼        ▼
List      Detail
Serializer Serializer
      │
      ▼
ViewSet
      │
      ▼
Router
      │
      ▼
API Endpoints
```

Endpoints now:

```
GET  /recipes/        → list
GET  /recipes/{id}/   → detail
POST /recipes/        → create
PUT  /recipes/{id}/   → update
DELETE /recipes/{id}/ → delete
```
