# 🍲 Django REST Framework – Recipe API Endpoints

## 🎯 Core Concept

In this section, we design the **Recipe API** that allows users to manage their recipes through a RESTful interface.

The goal is to implement a **CRUD API** where an **authenticated user** can:

- Create recipes
- List their recipes
- Retrieve recipe details
- Update recipes
- Delete recipes

> [!INFO]
> Every operation is **restricted to the authenticated user**.  
> This means users can **only access their own recipes**, not recipes created by others.

---

# 🏗️ Logic Flow

Typical **Django REST Framework request flow**:

```

Client Request  
↓  
URL Router  
↓  
View / ViewSet  
↓  
Serializer (validation + transformation)  
↓  
Model (Database)  
↓  
Response → JSON returned to client

```

Example Flow for retrieving recipes:

```

GET /api/recipes/  
↓  
RecipeViewSet  
↓  
RecipeSerializer  
↓  
Recipe Model (Database Query)  
↓  
JSON Response

```

# 🌐 API Endpoints Overview

The Recipe API exposes **two main endpoints**.

---

## 1️⃣ Recipes Collection Endpoint

```

/api/recipes/

````

This endpoint handles **listing and creating recipes**.

### Supported HTTP Methods

| Method | Purpose |
|------|------|
| **GET** | Retrieve all recipes for the authenticated user |
| **POST** | Create a new recipe |

Example requests:

```http
GET /api/recipes/
````

Returns:

```json
[
  {
    "id": 1,
    "title": "Pasta Carbonara",
    "time_minutes": 20,
    "price": "8.50"
  }
]
```

Creating a recipe:

```http
POST /api/recipes/
```

```json
{
  "title": "Chicken Curry",
  "time_minutes": 30,
  "price": "12.00"
}
```

---

## 2️⃣ Recipe Detail Endpoint

```
/api/recipes/{id}/
```

This endpoint manages **a specific recipe**.

Example:

```
/api/recipes/3/
```

### Supported HTTP Methods

|Method|Purpose|
|---|---|
|**GET**|Retrieve detailed information about a recipe|
|**PUT**|Fully update the recipe|
|**PATCH**|Partially update the recipe|
|**DELETE**|Delete the recipe|

---

### 🔍 Get Recipe Details

```http
GET /api/recipes/3/
```

Returns a **more detailed representation** than the list endpoint.

```json
{
  "id": 3,
  "title": "Chicken Curry",
  "time_minutes": 30,
  "price": "12.00",
  "description": "A spicy homemade curry recipe"
}
```

---

### ✏️ Update a Recipe

#### Full Update (PUT)

Replaces the entire object.

```http
PUT /api/recipes/3/
```

```json
{
  "title": "Updated Chicken Curry",
  "time_minutes": 35,
  "price": "13.00"
}
```

---

#### Partial Update (PATCH)

Only updates specific fields.

```http
PATCH /api/recipes/3/
```

```json
{
  "title": "Quick Chicken Curry"
}
```

---

### 🗑️ Delete a Recipe

```http
DELETE /api/recipes/3/
```

Removes the recipe from the database.

# 💻 Example Endpoint Structure

Typical DRF structure used for this API:

```
project/
 ├── recipes/
 │   ├── models.py
 │   ├── serializers.py
 │   ├── views.py
 │   ├── urls.py
 │   └── tests/
```

A ViewSet will usually power these endpoints.

```python
class RecipeViewSet(ModelViewSet):
    serializer_class = RecipeSerializer
    queryset = Recipe.objects.all()
```

> [!CODE]  
> `ModelViewSet` automatically provides:
> 
> - list
>     
> - create
>     
> - retrieve
>     
> - update
>     
> - partial_update
>     
> - destroy
>

# ⚡ Pro-Tips & Shortcuts

> [!INFO]  
> **REST Naming Convention**
> 
> Always use **plural resources** for endpoints.
> 
> Good:
> 
> ```
> /recipes/
> /recipes/{id}/
> ```
> 
> Bad:
> 
> ```
> /recipe/
> ```

---

> [!CAUTION]  
> Always filter recipes by **authenticated user**, otherwise users could access recipes from other users.

Example:

```python
Recipe.objects.filter(user=request.user)
```

---

> [!INFO]  
> **PUT vs PATCH**
> 
> - **PUT** → full object replacement
>     
> - **PATCH** → partial update
>     

Most APIs prefer **PATCH** for updates.
