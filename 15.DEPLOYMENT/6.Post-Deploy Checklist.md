# ✅ Post-Deploy Checklist

> Run this the first time you deploy, and again every time you deploy something you're nervous about.

---

## 1. Does Django agree that it's production-ready?

Django ships a checker. Use it.

```bash
docker compose -f docker-compose-deploy.yml run --rm app sh -c "python manage.py check --deploy"
```

It reports on the settings below. Every warning is something a real attacker has used against a real Django app.

| Setting | Value | What it does |
| --- | --- | --- |
| `DEBUG` | `False` | stops leaking stack traces, settings, and env vars on 500s |
| `SECRET_KEY` | 50+ random chars, not the default | see [[4.Environment Variables and Secrets]] |
| `ALLOWED_HOSTS` | your real domains, no `"*"` | blocks host-header poisoning |
| `SECURE_SSL_REDIRECT` | `True` | HTTP → HTTPS |
| `SESSION_COOKIE_SECURE` | `True` | session cookie never sent over plain HTTP |
| `CSRF_COOKIE_SECURE` | `True` | same for CSRF |
| `SECURE_HSTS_SECONDS` | `2592000` (30d) | browser refuses HTTP for this domain |
| `SECURE_CONTENT_TYPE_NOSNIFF` | `True` | stops MIME-sniffing attacks |
| `X_FRAME_OPTIONS` | `"DENY"` | clickjacking |

```python
# app/app/settings.py — only when not DEBUG
if not DEBUG:
    SECURE_SSL_REDIRECT = True
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True
    SECURE_HSTS_SECONDS = 2592000
    SECURE_HSTS_INCLUDE_SUBDOMAINS = True
    SECURE_CONTENT_TYPE_NOSNIFF = True
    SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
    X_FRAME_OPTIONS = "DENY"
```

> [!CAUTION] Enable HSTS last
> `SECURE_HSTS_SECONDS` tells browsers *"never speak HTTP to this domain again for N seconds."* If your TLS then breaks, visitors cannot reach the site at all — and you cannot undo it for them. Get HTTPS working first, then set a small value, then raise it.

## 2. Smoke test the actual API

```bash
curl -i https://your-domain/api/docs/
```

```bash
curl -i -X POST https://your-domain/api/user/create/ -H "Content-Type: application/json" -d '{"email":"smoke@test.com","password":"testpass123","name":"Smoke"}'
```

```bash
curl -i -X POST https://your-domain/api/user/token/ -H "Content-Type: application/json" -d '{"email":"smoke@test.com","password":"testpass123"}'
```

```bash
curl -i https://your-domain/api/recipe/recipes/ -H "Authorization: Token <paste-token>"
```

| Step | Expect | If not |
| --- | --- | --- |
| `/api/docs/` | `200` + Swagger UI | static files or nginx — see [[3.nginx as a Reverse Proxy]] |
| create user | `201` | check migrations ran |
| token | `200` + `{"token": …}` | user wasn't created, or password validation |
| recipes with token | `200` + `[]` | `401` means the header is wrong: `Token`, not `Bearer` |
| recipes **without** token | `401` | **a `200` here is a security incident** — your permission classes aren't applied |

That last row is the single most important line in this note. Always test the unauthenticated case.

---

## 3. Prove the isolation holds

Create a *second* user, add a recipe as user A, then list recipes as user B.

```bash
curl -s https://your-domain/api/recipe/recipes/ -H "Authorization: Token <user-B-token>"
```

Expect `[]`. If user B can see user A's recipes, `get_queryset()` is missing its `.filter(user=self.request.user)`.

## 4. Confirm the boring things

- [ ] `/admin/` loads **with CSS** → `collectstatic` and the shared volume are working
- [ ] Uploading a recipe image returns `200` and the URL it returns actually loads
- [ ] `docker compose -f docker-compose-deploy.yml ps` shows all three services `Up`
- [ ] Reboot the server; everything comes back on its own (`restart: always`)
- [ ] Logs are readable: `docker compose -f docker-compose-deploy.yml logs -f app`

## 5. Back up the database

An untested backup is not a backup.

```bash
docker compose -f docker-compose-deploy.yml exec db pg_dump -U $DB_USER $DB_NAME > backup-$(date +%F).sql
```

Then **restore it into a throwaway container** and confirm the row counts match. Do this once now, while nothing is on fire.

Automate it with cron:

```bash
0 3 * * * cd ~/recipe-api && docker compose -f docker-compose-deploy.yml exec -T db pg_dump -U user db > ~/backups/db-$(date +\%F).sql
```

> [!WARNING] Backups on the same server are not backups
> A disk failure or a compromised host takes the database *and* the backups. Sync them somewhere else — S3, Backblaze, another machine.

## 6. Know when it breaks before your users tell you

Minimum viable monitoring, all free:

| Need | Tool |
| --- | --- |
| "is it up?" | UptimeRobot / BetterStack — ping `/api/docs/` every 5 min |
| "what exploded?" | Sentry free tier — see [[11.Logging and Observability]] |
| "is the disk full?" | a weekly `df -h` reminder is genuinely enough at this scale |

## 🔁 The rollback plan

Write this down *before* you need it:

```bash
git log --oneline -5
```

```bash
git checkout <last-known-good-sha> && docker compose -f docker-compose-deploy.yml up -d --build
```

> [!CAUTION] Migrations don't roll back with your code
> Reverting the code does **not** revert the schema. If a deploy included a destructive migration (dropped column, renamed field), rolling back the code leaves you with a schema the old code doesn't understand. This is why additive migrations — add a nullable column, backfill, then remove the old one in a *later* release — are worth the extra step for anything that matters.
