## The complete refresher

### 1. What is a Django "project" vs an "app"?

- **Project** = the whole thing (`bureautech-api`). One project, created once: `django-admin startproject app .`
- **App** = a focused module inside the project — "products", "orders", "users". A project can have many apps. You create one anytime you need a new chunk of functionality:

```bash
docker compose run --rm app sh -c "python manage.py startapp core"
```

This generates a folder `core/` with `models.py`, `views.py`, `admin.py`, `apps.py`, `tests.py`, and a `migrations/` folder. **`urls.py` and `serializers.py` are not auto-created** — you add those files yourself when you need them.

The one thing people always forget: **a new app does nothing until you register it** in `config/settings.py`:

```python
INSTALLED_APPS = [
    ...
    "core",
]
```

### 2. The five files, in the order data actually flows

|File|Job|Analogy|
|---|---|---|
|`models.py`|Defines your data shape as Python classes|The spreadsheet's column headers|
|`migrations/`|Auto-generated diffs that turn models into real SQL tables|Git commits, but for your database schema|
|`admin.py`|Registers a model so it shows up in `/admin`|A free CRUD UI, zero work|
|`views.py`|The actual logic that runs when a URL is hit|The function that answers the phone|
|`urls.py`|Maps a URL path to a view|The phone number → which desk it rings|

### 3. The commands you'll run constantly

```bash
# Create a new app
docker compose run --rm app sh -c "python manage.py startapp <name>"

# After ANY change to models.py — generate the migration file
docker compose run --rm app sh -c "python manage.py makemigrations"

# Apply migrations to the actual database
docker compose run --rm app sh -c "python manage.py migrate"

# Create a login for /admin
docker compose run --rm app sh -c "python manage.py createsuperuser"

# Open a live Python shell with your models pre-loaded
docker compose run --rm app sh -c "python manage.py shell"

# Start the dev server (you already know this one)
docker compose up
```

The pattern you'll repeat forever: **edit `models.py` → `makemigrations` → `migrate`**. Forgetting that last step is the #1 "why isn't my change showing up" bug for everyone, always.

### 4. A model, annotated

```python
from django.db import models

class Category(models.Model):              # one class = one database table
    name = models.CharField(max_length=80)  # one attribute = one column
    slug = models.SlugField(unique=True)

    def __str__(self):
        return self.name                    # what shows up in admin/shell, not magic
```

`models.Model` is the base class that gives you `.objects.all()`, `.save()`, `.delete()` for free — that's the whole trick of an ORM.

### 5. Registering in admin — the fastest dopamine hit in Django

```python
# admin.py
from django.contrib import admin
from .models import Category

admin.site.register(Category)
```

Now `/admin/core/category/` exists with a full add/edit/delete UI, no HTML written by you.

### 6. A view + url, the minimal pair

```python
# views.py
from django.http import JsonResponse
from .models import Category

def category_list(request):
    cats = Category.objects.all()
    data = [{"id": c.id, "name": c.name} for c in cats]
    return JsonResponse(data, safe=False)
```

```python
# urls.py (inside the app)
from django.urls import path
from .views import category_list

urlpatterns = [
    path("categories/", category_list),
]
```

```python
# config/urls.py (the project-level one)
from django.urls import path, include

urlpatterns = [
    path("api/", include("core.urls")),
]
```

Hit `127.0.0.1:8000/api/categories/` and you get JSON back — no DRF needed yet, this is raw Django.
