# 🧪 Testing Patterns

> The idioms this project uses, in one place.

---

## 🏗️ Which base class

| Class | Database | Use for |
| --- | --- | --- |
| `SimpleTestCase` | ❌ none | pure functions, `wait_for_db` with mocks |
| `TestCase` | ✅ rolled back per test | **the default** |
| `TransactionTestCase` | ✅ truncated per test | testing `on_commit`, real transaction behaviour |
| `APITestCase` (DRF) | ✅ | same as `TestCase` + `self.client` is an `APIClient` |

```python
from django.test import TestCase
from rest_framework.test import APIClient
```

## 📐 The file layout

```text
app/
├── core/
│   └── tests/
│       ├── __init__.py
│       ├── test_models.py
│       ├── test_admin.py
│       └── test_commands.py
└── recipe/
    └── tests/
        ├── __init__.py
        ├── test_recipe_api.py
        ├── test_tags_api.py
        └── test_ingredients_api.py
```

> [!WARNING] The `__init__.py` everyone forgets
> Without it, `tests/` isn't a package and Django's test runner finds nothing. It reports "Ran 0 tests" and exits `0` — a green build that tested nothing.

## 🎭 The public/private split

Every API test file in this project:

```python
class PublicRecipeApiTests(TestCase):
    """Unauthenticated requests."""

    def setUp(self):
        self.client = APIClient()

    def test_auth_required(self):
        res = self.client.get(RECIPES_URL)
        self.assertEqual(res.status_code, status.HTTP_401_UNAUTHORIZED)


class PrivateRecipeApiTests(TestCase):
    """Authenticated requests."""

    def setUp(self):
        self.client = APIClient()
        self.user = create_user(email="user@example.com", password="test123")
        self.client.force_authenticate(self.user)
```

`force_authenticate` skips the token round trip — you're testing the endpoint, not the auth machinery. Test the auth machinery separately, once.

## 🏭 Helper factories

Put these at module level, above the test classes:

```python
def create_user(**params):
    """Create and return a new user."""
    defaults = {"email": "user@example.com", "password": "testpass123"}
    defaults.update(params)
    return get_user_model().objects.create_user(**defaults)


def create_recipe(user, **params):
    """Create and return a sample recipe."""
    defaults = {
        "title": "Sample recipe title",
        "time_minutes": 22,
        "price": Decimal("5.25"),
        "description": "Sample description",
        "link": "http://example.com/recipe.pdf",
    }
    defaults.update(params)
    return Recipe.objects.create(user=user, **defaults)


def detail_url(recipe_id):
    return reverse("recipe:recipe-detail", args=[recipe_id])
```

The `defaults.update(params)` pattern means each test overrides only what it cares about:

```python
recipe = create_recipe(user=self.user, price=Decimal("2.50"))
```

## 🌐 `APIClient`

```python
self.client.get(URL)
self.client.get(URL, {"tags": "1,2"})                    # query params
self.client.post(URL, payload)                           # dict → JSON
self.client.post(URL, payload, format="json")            # force JSON for nested data
self.client.post(URL, {"image": f}, format="multipart")  # file upload
self.client.patch(url, {"title": "New"})
self.client.put(url, full_payload)
self.client.delete(url)

self.client.force_authenticate(user=self.user)           # skip auth
self.client.credentials(HTTP_AUTHORIZATION="Token " + token.key)   # real header
```

> [!WARNING] `format="json"` for nested payloads
> The default encoding flattens nested structures. `{"tags": [{"name": "Vegan"}]}` arrives mangled and your test fails for a reason that has nothing to do with your code.

## ✅ Assertions

```python
self.assertEqual(res.status_code, status.HTTP_200_OK)
self.assertEqual(res.data, serializer.data)
self.assertIn("token", res.data)
self.assertNotIn("password", res.data)
self.assertTrue(Recipe.objects.filter(id=r.id).exists())
self.assertFalse(...)
self.assertIsNone(res.data.get("x"))
self.assertContains(res, "text")
self.assertRaises(ValidationError)

with self.assertNumQueries(3):
    self.client.get(RECIPES_URL)
```

Comparing against the serializer is the strongest list assertion available:

```python
recipes = Recipe.objects.all().order_by("-id")
serializer = RecipeSerializer(recipes, many=True)
self.assertEqual(res.data, serializer.data)
```

It checks the fields, the values, **and** the shape, in one line.

## 🔄 `refresh_from_db()`

```python
def test_update_recipe(self):
    recipe = create_recipe(user=self.user, title="Old")

    res = self.client.patch(detail_url(recipe.id), {"title": "New"})

    self.assertEqual(res.status_code, status.HTTP_200_OK)
    recipe.refresh_from_db()                       # ← without this it still says "Old"
    self.assertEqual(recipe.title, "New")
```

Your Python object is a snapshot of the row taken when you fetched it. The `PATCH` changed the row.

## 🎩 Mocking

```python
from unittest.mock import patch


@patch("core.management.commands.wait_for_db.Command.check")
def test_wait_for_db_delay(self, patched_check):
    """Test waiting for database when getting OperationalError."""
    patched_check.side_effect = [Psycopg2Error] * 2 + \
                                [OperationalError] * 3 + [True]

    call_command("wait_for_db")

    self.assertEqual(patched_check.call_count, 6)
    patched_check.assert_called_with(databases=["default"])
```

| | Meaning |
| --- | --- |
| `return_value` | what the mock returns every time |
| `side_effect = [a, b, c]` | return `a`, then `b`, then `c` |
| `side_effect = Exception` | raise it |
| `call_count` | how many times it was called |
| `assert_called_with(...)` | called with these arguments **last time** |
| `assert_called_once_with(...)` | called exactly once, with these |

> [!TIP] Patch where it's *used*, not where it's *defined*
> ```python
> # ❌ recipe.views already imported the name
> @patch("core.utils.send_email")
> # ✅
> @patch("recipe.views.send_email")
> ```
> This is the single most common mocking mistake. The patch appears to succeed and simply has no effect.

Also patch anything slow or external:

```python
@patch("recipe.models.uuid.uuid4")
def test_image_path(self, mock_uuid):
    mock_uuid.return_value = "test-uuid"
    path = models.recipe_image_file_path(None, "example.jpg")
    self.assertEqual(path, "uploads/recipe/test-uuid.jpg")
```

## 🖼️ Testing file uploads

```python
import tempfile
import os
from PIL import Image


class ImageUploadTests(TestCase):

    def setUp(self):
        self.client = APIClient()
        self.user = create_user()
        self.client.force_authenticate(self.user)
        self.recipe = create_recipe(user=self.user)

    def tearDown(self):
        self.recipe.image.delete()          # ← don't litter the filesystem

    def test_upload_image(self):
        """Test uploading an image to a recipe."""
        url = image_upload_url(self.recipe.id)

        with tempfile.NamedTemporaryFile(suffix=".jpg") as image_file:
            img = Image.new("RGB", (10, 10))
            img.save(image_file, format="JPEG")
            image_file.seek(0)                            # ← rewind before sending
            payload = {"image": image_file}
            res = self.client.post(url, payload, format="multipart")

        self.recipe.refresh_from_db()
        self.assertEqual(res.status_code, status.HTTP_200_OK)
        self.assertIn("image", res.data)
        self.assertTrue(os.path.exists(self.recipe.image.path))
```

Two things people miss: `image_file.seek(0)` (the file pointer is at the end after writing) and `tearDown` (test images accumulate in `MEDIA_ROOT` forever).

## 🏃 Running tests

```bash
docker compose run --rm app sh -c "python manage.py test"
```

```bash
docker compose run --rm app sh -c "python manage.py test recipe.tests.test_tags_api"
```

```bash
docker compose run --rm app sh -c "python manage.py test --shuffle"
```

```bash
docker compose run --rm app sh -c "python manage.py test --keepdb"
```

```bash
docker compose run --rm app sh -c "python manage.py test -v 2 --failfast"
```

| Flag | Effect |
| --- | --- |
| `--shuffle` | random order — **exposes tests that depend on each other** |
| `--keepdb` | reuse the test DB; much faster reruns |
| `--failfast` | stop at the first failure |
| `--parallel` | run across cores |
| `-v 2` | print each test name |

## 🎯 What to test

| Always | Rarely |
| --- | --- |
| Unauthenticated access is rejected | Django's own ORM |
| User A cannot see/edit user B's data | Getters and setters |
| Validation rejects bad input | Third-party library internals |
| The happy path returns the right shape | Every permutation of a field |
| Query count on list endpoints | |

**The permission tests are the ones worth writing most and the ones people skip.** See [[5.Custom Permissions]].

## ⚠️ Gotchas

- **"Ran 0 tests"** → missing `tests/__init__.py`, or files not named `test_*.py`.
- **Passes alone, fails in the suite** → shared state. `--shuffle` will prove it.
- **Assertion sees the old value** → missing `refresh_from_db()`.
- **List order mismatch** → the test and the view must use the same `order_by`.
- **Mock has no effect** → patched the definition site instead of the usage site.
- **`on_commit` callback never runs** → `TestCase` rolls back. Use `captureOnCommitCallbacks(execute=True)`.
